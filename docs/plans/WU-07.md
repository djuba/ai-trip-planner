# WU-07 — Contract suite (provider side): plan

**Status:** approved (2026-11-08) with the recommendations in §6, including Q5 (JUnit check built in WU-09) · **Depends on:** WU-05 (done on `main`), WU-06 (done in open PR #11) · **Author:** main agent (Opus), 2026-11-08

**Branch setup (user decision, 2026-11-08).** `main` is on hold. This unit branches from `wu/WU-06-api-nextjs-skeleton`, and its PR targets that branch, so it shows only WU-07 work. The implementation review diffs against that branch, not `main`. Stacked PRs get no CI (`verify.yml` runs only for PRs into `main`), so the local `pnpm verify` is the only gate until the PR is retargeted.

**Rule-parity design (user decision, 2026-11-08, after discussion).** The rule fixtures do **not** go through the black-box suite. Each backend sends every fixture through its own real `/v1/trip/extract` HTTP path with a mock `LlmClient`, at its integration layer, and compares exactly. A shared script then checks each backend's **JUnit XML** test report: every fixture `id` must appear as a passed test. This adds no contract change. The gap this leaves open is how strictly each backend's comparison checks; code review and a shared helper per language cover it. Rejected:
- A new `POST /v1/trip/validate` endpoint: a public endpoint that exists mainly for tests.
- A contract-defined mock mode for `/extract`: it would put a test double in the contract.
- Pact provider states: a pact generated from fixtures bends the consumer-driven model.

The fixture test and the results check need the mock `LlmClient` (WU-08) and the real `/extract` (WU-09), so they move to WU-09 as Notes. This unit writes the design into `CLAUDE.md` and ADR 0002.

**Review tier:** `sonnet` (user decision).

## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): a black-box suite that can prove any backend conforms. It is written before the real endpoints exist, so it runs against stubs first.

**In scope**
- **api-nextjs stubs** of `/extract`, `/recommend` and `/present` that return canned, schema-valid responses. `/present` streams.
- **`tests/contract/conformance/`:** health, 422 and 413 envelopes on every POST endpoint, response schemas, the `/present` stream, and CORS. Validation uses Ajv against `generated/*.schema.json`, never Zod.
- **`tests/contract/pact-verify.test.ts`:** a Pact verifier scaffold over `contracts/pacts/`. It skips cleanly while there are no pact files, and a hand-written wiring pact proves the verifier runs.
- **Self-test:** a fake backend returns one deliberately wrong field per check, and each check must fail.
- **Runner:** `pnpm test:contract` always starts its own api-nextjs. `pnpm test:contract:external` targets `API_BASE_URL`.
- **The rule-parity design written down:** `CLAUDE.md` §6.3/§6.5, ADR 0002, and the requirement in the `api-fastapi`/`api-go` READMEs.
- Feature doc `docs/features/contract-suite.md` (§6.2) and the README status rows.

**Out of scope**
- **Rule fixtures over HTTP, and the JUnit results check** (WU-09; see the decision above). The work breakdown's scope line "drives every `domain-schema/fixtures` case at `API_BASE_URL`" is replaced by this design. That's a change to this unit's own scope, recorded in its Notes at close.
- Real extract/recommend/present (WU-09–11). The stubs are deleted there.
- `needs_clarification` vs `ready` routing over HTTP. Stubs can't prove it, so it comes with WU-09's cassettes (Note).
- The Pact consumer and real pact files (WU-12).
- `LlmClient`, cassettes, `LLM_MODE` behaviour (WU-08).
- A `BACKEND=` switch in the runner (WU-15).

## 2. Approach & key decisions

| # | Decision | Why / CLAUDE.md | Rejected alternative |
|---|---|---|---|
| D1 | **Stubs return constants from `src/stubs/canned.ts`.** `/extract` → `ready` with a fixed profile. `/recommend` → one recommendation with an `unverified` claim and `critique.pass: true`. `/present` → a `PresentationModel` serialized to text and streamed in several chunks through a `ReadableStream`, `text/plain; charset=utf-8`. Each route uses `postRoute(<Request schema>, …)`; JSON stubs return via `jsonResponse`, and `/present` runs `PresentationModel.parse` before streaming. Every route exports `OPTIONS = preflight`. Each file is headed `// STUB — replaced in WU-0x`. | Unit scope; §5 streaming format; WU-06 note (`postRoute`, `jsonResponse`, `OPTIONS`). Chunked output exercises the adapter's stream pass-through over HTTP. | Fixtures from `@vp/domain-schema/testing` in non-test code: lint-blocked (§4.2). |
| D2 | **The suite is black-box.** It reads `generated/*.schema.json` and `generated/constants.json` from disk as JSON, and imports no TS from `apps/`, `backends/` or `packages/`. A `no-restricted-imports` block for `tests/contract/**` enforces this, as for journeys. | §6.5 "language-neutral"; WU-07 scope "not Zod". | Importing `@vp/domain-schema/wire` for types. |
| D3 | **Ajv 2020 strict + `ajv-formats`, every generated schema loaded first**, copied from `parity.test.ts` into `tests/contract/support/schemas.ts`, not imported. | WU-04 note. | Importing the parity helper: crosses D2's boundary. |
| D4 | **Checks are functions, tests are thin.** `conformance/checks/*.ts` export `checkX(baseUrl, …)` functions that throw an `AssertionError` with a readable message. `*.test.ts` files call them against the target URL, and the self-test (D7) calls the same functions against a fake backend. | So the required "deliberately non-conformant response" test can run the real checks. | `expect` inline in tests: the self-test would need Vitest inside Vitest. |
| D5 | **Checks require only what §5 specifies, not what api-nextjs happens to do** (review #1). A preflight must return any **2xx** status. `Access-Control-Allow-Origin` must equal `WEB_ORIGIN`. `Access-Control-Allow-Methods` must contain the requested method as a case-insensitive token, and `Allow-Headers` must cover `content-type` the same way. Content type is compared by media type only (`text/plain`, `application/json`), ignoring parameters such as `charset`. `contract-suite.md` states these rules. | §1/§6.5: the suite decides conformance for FastAPI and Go too. Starlette's CORS middleware answers preflights with 200. | Asserting 204 and exact header strings: fails valid backends. |
| D6 | **413 checks tolerate an early answer** (review #6). Oversized bodies are sent with an explicit `content-length` header, and a response that arrives before the upload finishes is normal. If the socket closes after a full 413 response, the check still passes; a reset *without* a response fails with a clear message. The **at-cap** case (exactly `maxRequestBodyBytes` → not 413) is **not** in the suite: every POST endpoint calls the LLM once real, so a valid 1 MiB request would need a 1 MiB cassette. It stays proven at the integration layer (WU-06 AC-API-04). | WU-06 note: 413 over real HTTP using `maxRequestBodyBytes`. Go's `MaxBytesReader` closes connections early. | Waiting for the whole upload: flaky on early-closing servers. |
| D7 | **Self-test with a fake backend** (review #5). `self-test/fake-backend.ts` is a `node:http` server whose default responses are **validated with Ajv when it's constructed**, so a drifting default fails with a clear message (§6.1 "mocks built through a validating helper"). A baseline case proves every check passes against it unmodified. Each further case overrides one response and asserts the matching check throws: wrong `contractVersion`; 422 with the wrong `code`; an oversized body answered with 422; an `ExtractResponse` with an unknown `status`; a `RecommendResponse` missing `critique`; a `/present` body with SDK framing (`0:"…"`); a `/present` body that is truncated JSON; missing `Access-Control-Allow-Origin`. Two more cases must **pass**: a 200 preflight (D5), and a 413 sent before the upload ends, followed by a socket close (D6). It runs in the `unit` project and needs no backend. **This self-test is the Definition-of-done proof** that one invalid field fails the suite. | WU-07 "Required tests" and DoD. | Proving the DoD only by mutating a stub: that proves the backend's outgoing `jsonResponse` guard (a 500), not the suite's schema checks. |
| D8 | **Runner, split into a pure decision and a thin shell** (review #2, #3, #7). `scripts/contract/plan-run.ts` exports `planRun(argv, env)`, which returns `{ startServer: true }` by default, or `{ startServer: false, baseUrl }` under `--external`. It errors when `--external` is given without `API_BASE_URL`. By default, an exported `API_BASE_URL` is ignored, with a printed notice. `scripts/run-contract.ts` acts on the decision. When starting a server, it reuses `backends/api-nextjs/tests/support/{build-once,api-server}.ts`. It always prints the target URL and whether it started the server. It calls `stop()` in `finally` **and** on `SIGINT`/`SIGTERM`, and exits with Vitest's code. Root scripts: `test:contract` = `node scripts/run-contract.ts` (used by `verify`), and `test:contract:external` = `node scripts/run-contract.ts --external`. | The gate must always test this branch's api-nextjs. An exported URL pointing at a live dev server would cost money after WU-09. The runner is root tooling, so it may reuse the backend harness; the *suite* knows only its target URL (WU-06 note). | `verify` honouring `API_BASE_URL`: the gate could silently test something else. A copy of the harness: two places to fix Windows kill bugs. |
| D9 | **Vitest project `contract`** includes `tests/contract/conformance/**/*.test.ts` and `tests/contract/pact-verify.test.ts`, which are excluded from `unit`. `unit` keeps `tests/contract/self-test/**` and `scripts/contract/*.test.ts`. The target is `CONTRACT_TARGET_URL`, which the runner sets. Run directly, it defaults to `http://localhost:4000` (a running `pnpm dev`). | §3 default; §6.3 layers. A separate variable name means a shell's `API_BASE_URL` reaches the suite only through `--external`. | Reading `API_BASE_URL` in the suite: would bypass D8's guard. |
| D10 | **Pact verify scaffold.** It lists `contracts/pacts/*.json`. With none, it runs one `it.skip` titled `AC-CONTRACT-08: …(written by WU-12)`. With files, it runs `new Verifier({ provider: 'vacation-api', providerBaseUrl, pactUrls }).verifyProvider()`. A **wiring pact** `tests/contract/support/wiring.pact.json` (Pact v4, one `GET /v1/health` interaction, matching `status`) is always verified, in a passing test also titled AC-CONTRACT-08 (review #7). `PACT_DO_NOT_TRACK=true` is set. `contracts/pacts/.gitkeep` keeps the directory. | §6.5 committed pacts, no broker, no hosted services. Moves native-verifier risk out of WU-12. | No wiring pact: the first verifier run would be in WU-12. |
| D11 | **Dependencies (dev only, in `tests/contract`):** `ajv`, `ajv-formats` (catalog), `@pact-foundation/pact` (new exact catalog pin, the newest that passes pnpm's release age), `vitest`. `allowBuilds: '@scarf/scarf': false` blocks Pact's telemetry postinstall. The Pact dependency lands in the Pact commit (review #7). | §3 exact pins; §10 one logical change per commit. | — |
| D12 | **Rule parity written down, implemented in WU-09.** `CLAUDE.md` §6.5 replaces "sends every `domain-schema/fixtures` case to `API_BASE_URL`… covers every rule code" with the per-backend design. Each backend's integration suite sends every fixture through its real `/extract` with a mock `LlmClient` that returns the fixture's profile. It checks that the normalized profile equals the fixture's profile, so `normalize` can't change a case. It compares violations exactly, in order, and titles each test `RULE-FIXTURE <file>/<id>`. A shared script, `tests/contract/rule-results.ts`, built in WU-09, checks a backend's JUnit XML report: every fixture `id` must appear as passed. §6.3's api-nextjs integration bullet gains the fixture test. **ADR 0002** records the options weighed and the gap left open (comparison strictness, covered by a shared helper per language and code review). The `api-fastapi`/`api-go` READMEs list it as a requirement. | User decision above; §9: those READMEs state the contract a backend must satisfy. | Building `rule-results.ts` now: there is no HTTP fixture test to check until WU-09. |

**Open**
- **Q5 — Where the JUnit check lives.** Recommend building it in WU-09, next to the first HTTP fixture test (D12). The alternative is building it now and proving it against the domain-schema unit fixture tests. That proves the mechanism early, but checks the wrong layer.

**Risks**
- **R1 — Pact on Windows.** The native core may not load. T4 tests this first; if it fails, I'd stop and ask before dropping the wiring pact.
- **R2 — Pact's dependency tree** is dev-only, so `pnpm audit --prod` skips it. T6 reviews a full `pnpm audit` and reports high-severity advisories rather than suppressing them.
- **R3 — `/extract` and `/recommend` conformance needs cassettes from WU-09/10.** AC-CONTRACT-05/06 will go through the LLM once the stubs are gone, so each backend needs replay cassettes for those exact requests (Notes).
- **R4 — Stale stubs.** File headers and Notes on WU-09/10/11.
- **R5 — Node running `scripts/run-contract.ts` that imports the harness `.ts` files** relies on type stripping, as `gen` does. T2 proves it.
- **R6 — Rule parity across backends is unproven until WU-09.** Until then, only the TS unit fixture tests exist (`rule-fixtures.ts`). The README row says so.
