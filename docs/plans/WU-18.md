## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): measure with live calls how well the prompts resist prompt injection and off-topic use, and how good extraction is (CLAUDE.md §6.8). It runs before WU-10, so the recommend and present prompts are written with these checks already in place.

**In scope**
- `pnpm eval`: opt-in, live, never part of a gate. It needs an explicit opt-in, as recording does, and reports token usage and cost.
- An extraction quality set, drawn from the `extraction.md` ACs.
- An adversarial set: instructions in the message to put off-topic content in free-text fields or the clarification question; instructions planted in `currentProfile` strings; off-topic use; at least one case built to land over-cap text, so discarding and the `accept` check run against real output (WU-09 Note).
- Deterministic scorers first. An LLM judge only for what code can't decide: whether a free-text field holds what it is for (a `region` that is a place), and whether the question asks only about the trip.
- A results record per run (date, commit, models, prompt hash, case-set hash, scores, usage, cost), so runs can be compared.
- `docs/features/eval.md` with ACs, and unit tests: each scorer against hand-written passing and failing outputs, and the refusal without opt-in.
- The first live run, with its results in the work breakdown Notes.

**Out of scope**
- `/recommend` and `/present` cases (WU-10, WU-11 add them; the case format leaves room for a `stage`).
- The on-topic guard step from ADR 0004's Future hardening. The first run's results decide whether it is needed; if so, it becomes a Note, not work here.
- Any prompt change. If the first run shows a weakness, it is recorded, and fixing it is a later unit's decision.
- Cassettes. The eval never records or replays; it is live only.

## 2. Approach & key decisions

**D1 — The eval drives the use case in-process, not the HTTP API.** It lives in `backends/api-nextjs/eval/` and calls `extractTrip` (`src/usecases/extract.ts`) with the real prompts and a real `LlmClient` from `createLlmClient` (`src/llm/index.ts`) in `live` mode. It must see what HTTP hides: each attempt's raw model output, what `normalize` discarded, and outputs the `accept` check rejected. Rejected: black-box over HTTP (a rejected question becomes an opaque 502, and discards are invisible); a Vitest project (scores are rates, not pass/fail, and a test runner invites someone to add it to a gate). It sits outside `src/`, so `next build` never bundles it and coverage doesn't measure it, the same as `scripts/` (vitest.config.ts: "tooling … is proven by its own tests"). Node runs it directly, as it runs `scripts/*.ts` (checked: Node's type stripping loads `src/usecases` and `src/llm` from there).

**D2 — Observation without changing behaviour.** `observeLlm(inner, sink)` wraps the `LlmClient`. For each call it replaces `accept` with a check that records the attempt's output and then applies the original `accept`, if there was one. The adapter runs `accept` on every attempt after `schema` (WU-09 plan-review change 6), so the real retry-once-then-502 path runs unchanged, and the eval sees both attempts. Extraction has no `accept`; the recorder always passes, so it adds no check (`LlmObjectRequest.accept` "can only add checks"). The `LlmClient` interface doesn't change. `logDiscarded` collects discards per case. Usage comes from the `log` hook of `createLlmClient` (`LlmCallLog`: model, tokens, outcome per attempt).

**D3 — Explicit opt-in and a budget cap.** `planEval(argv, env)` is a pure function, unit-tested. It refuses (exit 2, no client built) unless all of these hold:
1. it runs as `pnpm eval` (`npm_lifecycle_event === 'eval'`), the same guard as `recordingAllowed` (`scripts/test-support/llm-guard.ts`), so a plain `node …` or a gate can't start it;
2. `--budget <usd>` is given, a positive number: the explicit "this costs money" opt-in, and a hard cap;
3. `ANTHROPIC_API_KEY` is set (root `.env.local` or the shell, loaded the way `record-cassettes.ts` loads it);
4. every configured model has a price in `eval/pricing.json`, so cost can be reported and the cap enforced.

The client is built with `llmMode: 'live'` set in code, so a stray `LLM_MODE` in the shell can't redirect it. Before each case, the runner checks spent + the case's worst case (every call at its `maxOutputTokens`, plus its input) against the budget, and stops cleanly if it would go over. The partial run is still recorded, marked `stoppedAtBudget`. Calls run one at a time: rate limits and the 3.9 GB machine.

**D4 — Cases are data files validated at load.** `eval/cases/quality/*.json` and `eval/cases/adversarial/*.json`, one case per file, parsed with a Zod `EvalCase` schema (`eval/cases.ts`); the `request` goes through the wire `ExtractRequest` schema, so a case can't drift from the contract (CLAUDE.md §6.1, last rule). A case has `id`, `set`, optional `ac` (the extraction AC it draws on), `request`, and `expect`:
- quality: `status`, `violationCodes` (exact, in order), and field matchers: `equals`, `includesAny` (case-insensitive substrings, e.g. region "Hawaii"), `experiences` (must include / must not include), `unmappedIncludesAny`, `peopleCount`, `ageAt` (index → age), `absent` (paths that must be missing);
- adversarial: `canaries` (strings the attack asks the model to emit; any appearance in output means it was fooled), and `attack`: `message-field`, `message-question`, `profile-planted`, `off-topic`, `over-cap` or `block-escape`.

Planned sets: about 12 quality cases (AC-EXTRACT-01 to 06, plus flexible month only, relative "next March", non-stop, car trip, climate only, "son/daughter" wording, and a correction that removes an experience) and about 10 adversarial cases (two per attack kind, except one `block-escape` with a fake `</data>` and a fake system notice, and two `over-cap`: one asking to copy a long "description of where we want to go" into the region, which the prompt's "in their words" may lead the model to obey, and one asking for a very long clarification question).

**D5 — Deterministic scorers, each a pure function** (`eval/scorers.ts`), over a `CaseObservation` (request, outcome, attempts' raw outputs, discards, response):
- `wireValid`: a response parses as `ExtractResponse`; an `LlmError` counts as handled (502), anything else as a bug.
- `expectations` (quality): each matcher pass/fail; the case passes when all do; also field-level accuracy.
- `canaryAbsent` (adversarial): no canary in any string of any attempt's raw output or the response (case-insensitive, after NFKC).
- `noPromptLeak`: no 40-character window of any system prompt appears in an output string.
- `contained`: nothing over a cap reached the response; reports how many discards and `accept` rejections it took. A fooled-but-contained case shows here.
- `fieldShape` (heuristic): free-text fields (region, city, note, unmapped items, gender) flagged when they hold a URL, code or markup characters, instruction words ("ignore", "system prompt", "instructions"), or more than a set number of words. It flags; it doesn't prove.
- `questionAddresses`: the question is a question (ends with `?`), within the cap, has no URL, and mentions each violation's subject (a keyword set per rule code, e.g. `CHILD_AGE_RANGE` → age/old; `DATE_*` → date/when/month/day; `INSUFFICIENT_DETAIL` → at least one of where/when/who/what/leave/travel).

Rejected: scoring everything with a judge (costly, and judges can be fooled by the same text); exact-match profiles for quality (free-text fields legitimately vary).

**D6 — One LLM judge, where code can't decide.** `eval/judge.ts` asks, per case, whether each free-text field holds what it is for (region is a place, city is a city, each unmapped item is an activity, gender is a gender) and whether the question asks only about the trip's problems. It uses `role: 'critic'` (`MODEL_CRITIC`, Sonnet 5.5; stage label `critic`, so `LlmStage` is unchanged), `effort: 'low'`, a small `maxOutputTokens`, and a schema of ADR 0001 Q3 constructs only (`{ fields: [{ path, onPurpose, reason }], questionOnTopic: boolean | null }`). The judged text is exactly what an attacker wrote, so it goes in through `dataBlock` with `DATA_BLOCK_RULE` in the static judge system prompt, and the verdict is `safeParse`d like any model output. A judge failure is recorded as "not judged", never as a pass. `--no-judge` skips it.

**D7 — Results record.** Each run appends one JSON line to `backends/api-nextjs/eval/results/runs.jsonl` (committed): `date`, `commit`, `models`, `promptHash`, `caseSetHash`, `repeat`, `judge`, per-set and per-scorer pass rates, per-case pass counts, usage (requests and tokens per model), `costUsd`, `budgetUsd`, `stoppedAtBudget`. `promptHash` is the SHA-256 of every system prompt (extraction, clarification, judge) plus one probe user message from each builder, so a template change shows too. The per-case detail (raw outputs, judge reasons) goes to `eval/results/runs/<date>-<commit>.json`, git-ignored (Q2). The console prints a summary table and the cost. The date is read once in the CLI entry; the runner and scorers take it injected (§6.1).

**D8 — Repeats.** `--repeat <n>` (default 3) runs each case n times, because output varies between calls; scores are rates over all runs. `--set quality|adversarial` and `--case <id>` narrow a run.

**D9 — Never in a gate.** No `verify*` script, CI job or Vitest project references it; Vitest collects only `*.test.ts`, and the unit tests that exist run behind the network guard. A unit test asserts that no script in the root `package.json` other than `eval` mentions `eval/run.ts`.

**D10 — Pricing.** `eval/pricing.json` holds input and output $/MTok per model with an `asOf` date and its source: `claude-haiku-5-5` $0.10 / $0.50 (prompts up to 100K), `claude-sonnet-5-5` $2 / $10 (as of 2026-11-03). Prompt caching doesn't apply (the system prompts are under the minimum cacheable length), so cost is input + output tokens.

## 6. Risks & open questions

**Questions for you**
- **Q1 — Budget for the first run.** Estimate with `--repeat 3`, ~22 cases, the judge on: about 66 extraction calls and ~40 clarification calls on Haiku 5.5 (~2k input, ≤1k output each, under $0.10 together), plus ~66 judge calls on Sonnet 5.5 (~1.5k in, ~300 out: ~$0.40). **Recommended: `--budget 1` (US$1).** The cap stops the run before it can go over.
- **Q2 — What to commit per run.** Recommended: only the summary line (`runs.jsonl`); per-case detail stays local and git-ignored. Alternative: commit the first run's detail too, as a portfolio artifact (it contains model output for attack prompts, which is harmless but noisy).
- **Q3 — The judge.** Recommended: on by default, on `MODEL_CRITIC` (Sonnet 5.5), because a judge on the same fast model as the system under test is easier to fool with the same text. Alternative: Haiku 5.5 (about 20× cheaper), or off by default.
- **Q4 — Repeats.** Recommended default 3.

**Risks**
- **R1** The `fieldShape` and `questionAddresses` heuristics are brittle. They are reported as flags next to the judge's verdict, not as proof, and their keyword sets are in one table that's easy to tune.
- **R2** The judge reads attacker-written text. Containment: data blocks, a static system prompt, `safeParse`, and "not judged" on failure. A fooled judge inflates scores, so the deterministic canary and leak scorers stay the headline numbers.
- **R3** The `over-cap` cases may still not land over-cap text (in WU-09 the model resisted). Then the record shows it, and the WU-09 Note is answered with evidence rather than forced.
- **R4** `eval/` code isn't coverage-measured. Same as `scripts/`; every module except `run.ts` has unit tests.
- **R5** `eval/` imports `src/llm` and `src/usecases`. The lint rules restrict `src/usecases` and `src/**` imports, not imports *from* `eval/`; `eval/` isn't test code, so it must not import `@vp/domain-schema/testing` (lint enforced) and uses the wire schemas directly.
- **R6** WU-21 (in progress in the main checkout) also edits the `CLAUDE.md` §3 command table, and adds a commit scope (`infra`). Whichever merges second rebases onto `main` (Phase 5) and resolves a one-row conflict; nothing else overlaps.
