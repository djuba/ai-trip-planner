## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): decide how the app is hosted, and build the API as a container image that CI checks against the contract. The image is the artifact that will ship, and CI proves it conforms before anything is hosted.

**In scope**
- **ADR 0005, "Hosting and access":** goals (1a portfolio, 1b platform skills), threat model, budget, no user accounts, closed-beta option, no Kubernetes, Terraform, one environment built early and launched late; a short cloud comparison with a recommendation; the invite-code gate over Cloudflare Access; OIDC deploy credentials; `max instances = 1`; one image across LLM modes with cassettes baked in; `NEXT_PUBLIC_API_BASE_URL` inlined at web build time; custom domain optional; what would change for a product.

- **`pnpm test:image`**: one command that builds the image, checks it (non-root, no secrets), runs it in replay mode and runs `pnpm test:contract:external` against it. Not part of `pnpm verify`.
- **CI:** an `image` job in `.github/workflows/verify.yml` that runs `pnpm test:image`.

## 2. Approach & key decisions

**D1. Standalone output only inside the image build.** `next.config.mjs` sets `output: 'standalone'` only when `NEXT_OUTPUT=standalone`, which only the Dockerfile sets. Local and CI builds stay as they are, so `next start` keeps working for the functional tests and `pnpm test:contract` (the WU-20 Note's risk), and `pnpm verify` is unchanged.
*Rejected:* always-standalone with the test harness switched to `node .next/standalone/.../server.js`. It would change every functional and contract run in this unit, and Next's standalone trace copies pnpm's symlinked `node_modules`, which fails on Windows without Developer Mode. "Test what you ship" is kept by the image job testing the image itself (D5).

**D2. A `.dockerignore` allowlist.** It starts with `*` and re-includes only what the build needs: root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `tsconfig.base.json`, `backends/api-nextjs/`, `packages/domain-schema/`, `.llm-cassettes/api-nextjs/`, then re-excludes `**/node_modules`, `**/.next`, `**/.env*`. A new file anywhere (an `.env.local`, a key file) stays out of the build context by default. That's the "no secrets in any layer" guarantee; no `ARG` or `ENV` holds a secret either. If pnpm's frozen install needs the other workspace `package.json` files to match the lockfile, they're added to the allowlist (manifests only).
*Rejected:* a denylist `.dockerignore`, which is only as safe as its last update.

**D3. The Dockerfile** (CLAUDE.md §3, §8.3):
- Base `node:24.22.1-bookworm-slim` (matches `.nvmrc`), pinned by digest, `--platform=linux/amd64`.
- `deps`: copy the lockfile and workspace manifest, `corepack enable`, `pnpm fetch` (cached layer), then copy sources and `pnpm install --offline --frozen-lockfile --filter @vp/api-nextjs...`, with install scripts off (lefthook's `prepare` needs `.git`; `allowBuilds` already blocks the rest).
- `build`: `NEXT_OUTPUT=standalone NEXT_TELEMETRY_DISABLED=1 pnpm --filter @vp/api-nextjs build`.
- `runtime`: a fresh slim base; copy `.next/standalone` and `.llm-cassettes/api-nextjs`; `USER node`; `ENV NODE_ENV=production HOSTNAME=0.0.0.0 PORT=8080 LLM_CASSETTE_DIR=/app/.llm-cassettes/api-nextjs`; `CMD ["node", "backends/api-nextjs/server.js"]`. `HOSTNAME` must be set: Docker sets it to the container ID, and Next's standalone server binds to it. Port 8080 is Cloud Run's default (WU-21).
- **Mode defaults:** `LLM_MODE=replay` and the §8.1 model IDs as `ENV` defaults, so a bare `docker run` costs nothing and needs no key. Live mode (WU-23) overrides them with `-e`/service env. These are configuration, not logic (§8.1).
  *Rejected:* no defaults, so every run must pass five variables. Config already fails fast when they're missing, but replay-by-default is the safer failure mode for an image anyone can run.

**D4. The image test uses the contract runner's model IDs.** Cassette keys hash the request body, which includes the model ID. `pnpm test:contract` starts api-nextjs with `MODEL_*=test-model-*` (`backends/api-nextjs/tests/support/api-server.ts`), so any cassette the contract suite replays (from WU-09) is keyed on those. `pnpm test:image` passes the same values to the container, read from a constant exported by `api-server.ts` (`CONTRACT_TEST_ENV`, a small refactor of `baseEnv`). Otherwise the image would pass today, with stub endpoints, and start failing at WU-09 for a reason unrelated to the image. Proposed Note for WU-09.

**D5. `scripts/test-image.ts` (`pnpm test:image`), one command for local and CI** (§6.7: each gate is one command; §3: no bash-only syntax, so a Node script, not shell in YAML):
1. `docker build --platform linux/amd64 -f backends/api-nextjs/Dockerfile -t vp-api-nextjs:test .` (`--no-build` skips it when CI has built already, if useful).
2. **Checks** (AC-IMAGE-02/03): the container's `process.getuid()` is not 0 (run with `--entrypoint node`); `docker image inspect` shows no `ANTHROPIC_API_KEY` and no variable whose name contains `KEY`, `SECRET` or `TOKEN`; no `.env*` file exists under `/app`.
3. Runs the container detached on a free loopback port with `WEB_ORIGIN=http://localhost:3000` and the D4 env, and waits for `GET /v1/health`.
4. Runs `node scripts/run-contract.ts --external` with `API_BASE_URL` set to the container.
5. Always removes the container; prints `docker logs` on failure.
The argument building and the env/secret checks are pure functions in `scripts/image/plan-image.ts`, unit-tested like `scripts/contract/plan-run.ts`. The orchestration is a thin wrapper, like `run-contract.ts`.

**D6. CI: a separate `image` job in `verify.yml`, parallel to `verify`.** Ubuntu runners have Docker. Steps: checkout, pnpm, Node, `pnpm install --frozen-lockfile`, `pnpm test:image`. `permissions: contents: read`, no secrets, no cloud access (deploy credentials come in WU-21 through OIDC, in a separate workflow). A separate job keeps `verify` unchanged and lets its result show on its own. Whether it becomes a required check is **Q2**.

**D7. ADR 0005** follows the ADR 0004 format (Context, Decision, Consequences, Alternatives), with the work breakdown's Direction as its decisions. The cloud comparison is a table: Cloud Run (recommended: scale to zero, a free tier that covers this traffic, streaming responses, Workload Identity Federation for GitHub OIDC), AWS App Runner and ECS Fargate (Fargate needs a load balancer that costs money while idle; App Runner's position is checked), and a line each on Fly.io, Vercel and a VPS. Prices and free-tier figures are checked against the providers' current pages while writing, and dated in the ADR, not written from memory. Status `accepted` once you approve the commit.

**D8. Acceptance criteria live in this plan**, as in earlier infrastructure units. This unit adds no user-facing feature, so there's no `docs/features/` file.

## 6. Risks & open questions

**Q1 (blocking): Docker isn't installed on this machine.** T3 and T4 need it, and the workflow verifies a unit before committing anything, so CI alone can't be the first place the image is built. Options:
- **(a) Recommended: install Docker Desktop** (WSL 2 backend) before the build. Memory is tight (~3.9 GB; see the saved note), so I'd cap the WSL VM (`.wslconfig`, `memory=2GB`) and never run `pnpm verify` and `pnpm test:image` at the same time. The WU-20 Note already expects Docker for this unit.
- (b) Build everything except the image locally, then iterate the Dockerfile through CI on the draft PR. Every push runs the full `pre-push` gate locally (~minutes each), and the code would be pushed before the walk-through, which breaks Phase 2–3's order. I'd only do it if (a) isn't possible.

**Q2: Make `image` a required check?** Recommended **yes**: it's the only proof the shipped artifact conforms, and a docs-only PR costs a few minutes of free runner time. Adding it to branch protection is a GitHub setting; I'd give you the `gh api` command (or run it, if you say so) after the PR's first green run, since a required check must have reported once before it can be selected.

**R1: pnpm frozen install with a partial workspace.** With only two workspace packages in the build context, `--frozen-lockfile` may report the lockfile out of date. The fix is copying the other workspace manifests (D2), or `pnpm deploy`. Found during T3; recorded as a deviation only if the approach changes.

**R2: `ai/test` in the bundle** (WU-08 R2). No route imports `src/llm` yet, so the standalone trace doesn't include it. WU-09 is the first unit to bundle it; the `image` job will catch a breakage then.

**R3: Build memory.** `next build` inside Docker on a ~2 GB VM may be slow or OOM. If so, I'd raise the VM's memory temporarily, not change the build.

**R4: Stub endpoints.** The contract suite currently runs against WU-07's stubs, so the image proves wiring, CORS and the stream path, not LLM replay. From WU-09 the same job proves cassettes replay inside the image (D4).
