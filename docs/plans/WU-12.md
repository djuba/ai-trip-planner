## 1. Goal & scope

**Goal** (work breakdown): the web app exists, talks only to `NEXT_PUBLIC_API_BASE_URL`, and publishes its expectations as a pact.

**In scope**
- `apps/web-nextjs` as a real Next.js App Router app on :3000: Tailwind, shadcn/ui, a base layout and a landing page. The page shows a small API status line (from `GET /v1/health`) so the shell exercises the client end to end and the functional tests have states to check.

It imports only `@vp/domain-schema/wire`, sends `Authorization: Bearer <code>` when it has a code, `safeParse`s every JSON response, and maps every failure to a typed error (401, 429 `RATE_LIMITED` vs `QUOTA_EXHAUSTED`, 413, 422, 502, 500, network, abort, contract violation).

- `docs/features/web-client.md` with the ACs; README "How the design is checked" Pact row → Built.

## 2. Approach and key decisions

**D1. One app, plain Next.js App Router, no server features.** `src/app/layout.tsx` + `src/app/page.tsx`, client components where they fetch. No Server Actions, no route handlers, no API key (CLAUDE.md §9). `next.config.mjs` follows the api-nextjs pattern: `transpilePackages: ['@vp/domain-schema']`, `agentRules: false`, `turbopack.root` = repo root, `poweredByHeader: false`, root `.env.local` loaded the same way (WU-06 note). Scripts: `dev` = `next dev --port 3000`, `build`, `start` = `next start --port 3000`.

**D2. Tailwind v4 + shadcn/ui, components copied in.** Tailwind v4 via `@tailwindcss/postcss` and a CSS-first `globals.css` (shadcn's default tokens). shadcn/ui is "copy the component source": `components.json` + `src/lib/utils.ts` (`cn`) + only the components this unit uses (`button`, `card`, `badge`), with their deps (`class-variance-authority`, `clsx`, `tailwind-merge`, `@radix-ui/react-slot`). I'll generate them with the shadcn CLI at a pinned version (`pnpm dlx shadcn@<exact> add …`) and review the output; if the CLI wants network registry access I can't get, I'll write the same files by hand from shadcn's source. *Rejected:* a component library dependency (CLAUDE.md §9 says Tailwind + shadcn/ui only); CSS modules or inline styles (§9).

**D3. The client returns a `Result`, never throws for HTTP outcomes.**
```ts
type ApiResult<T> = { ok: true; data: T } | { ok: false; error: ApiError };
type ApiError =
  | { kind: 'unauthorized' }                                   // 401 UNAUTHORIZED
  | { kind: 'rate_limited'; retryAfterSeconds: number | null } // 429 RATE_LIMITED (+ Retry-After)
  | { kind: 'quota_exhausted' }                                // 429 QUOTA_EXHAUSTED
  | { kind: 'message_too_long' }                               // 413 PAYLOAD_TOO_LARGE (WU-06 note)
  | { kind: 'invalid_request'; message: string }               // 422 VALIDATION_FAILED
  | { kind: 'upstream'; refusal: boolean }                     // 502 LLM_REFUSAL / LLM_UPSTREAM_ERROR
  | { kind: 'server'; status: number }                         // 500, unknown status or error body
  | { kind: 'network' }                                        // fetch rejected
  | { kind: 'aborted' }                                        // AbortSignal fired
  | { kind: 'contract'; detail: string };                      // 2xx body fails the wire schema
```
Branching uses `status` + `error.code`, never `message` (§4.5 "messages are not part of the contract"). An error body that isn't an `ErrorResponse` falls back by status. WU-13's reducer can switch on `kind` without try/catch. *Rejected:* throwing an `ApiError` class (forces try/catch in every caller and loses exhaustiveness checks).

**D4. Client construction is injected, not global.** `createApiClient({ baseUrl, getInviteCode, fetch? })`. `baseUrl` comes from `src/lib/api/config.ts`, which reads `process.env.NEXT_PUBLIC_API_BASE_URL` and nothing else (§5), trims a trailing slash, and fails loudly if it is missing. `getInviteCode()` returns `string | undefined`; the header is sent only on trip endpoints and only when a code exists (health is open, AC-GATE-04). Where the code is stored (sessionStorage after a WU-13 prompt) is WU-13's decision; this unit ships an in-memory default that returns `undefined`. Injected `fetch` keeps unit tests free of `msw`.

**D5. Response validation with the wire schemas.** Every JSON 2xx body is `safeParse`d against `HealthResponse`, `ExtractResponse` or `RecommendResponse` (§7 "untrusted input" applies to the client too; §4.2 allows the web app to import wire schemas). `present()` returns the raw `ReadableStream` on 200, and the caller runs the final `safeParse` on the completed object (§5; WU-14).

**D6. Pact consumer design (the risky part).**
- Tests live in `apps/web-nextjs/tests/contract/vacation-api.pact.test.ts`, use `PactV4` from `@pact-foundation/pact` (catalog) and drive the **real API client** against the Pact mock server, so the pact records what the client actually sends.
- Consumer `web-nextjs`, provider `vacation-api` → `contracts/pacts/web-nextjs-vacation-api.json` (WU-07 note). The file is deleted before the consumer run so it never accumulates stale interactions, then written fresh and committed.
- **Replay constraint:** the verifier replays these requests against api-nextjs in `LLM_MODE=replay`, and cassettes are keyed by the model request, which is built from the HTTP request. So every LLM-backed interaction reuses a request body the conformance suite already sends (`tests/contract/conformance/checks/requests.ts`), and its existing cassette replays. No new recording, no live calls. The consumer can't import that file (it's black-box tooling), so the bodies are copied, built through `buildFixture`, and a comment names their source. A provider run that misses a cassette fails loudly ("re-record…", §6.1), so drift can't pass silently.
- **Matching:** requests are matched exactly (they are ours). Responses use type matchers (`like`, `eachLike`, regex on enums and status literals), because model-written text is not the contract. `status: 'needs_clarification' | 'ready'` and error `code`s are matched exactly, since the client branches on them.
- **Interactions** (all gated ones carry `Authorization: Bearer <example code>`, matched by regex `^Bearer \S+$`):
  1. `GET /v1/health` → 200 `{ status: 'ok', contractVersion: like('0.6.0') }`, no Authorization.
  2. `POST /extract` vague message → 200 `needs_clarification` with `violations: eachLike({ code, path, params })` and a non-empty `clarificationQuestion`.
  3. `POST /extract` complete profile + confirmation → 200 `ready`.
  4. `POST /extract` empty message → 422 `VALIDATION_FAILED` (no model call).
  5. `POST /recommend` ready profile → 200 `RecommendResponse` shape.
  6. `POST /recommend` profile with no adult → 422 `VALIDATION_FAILED`.
  7. `POST /present` → 200, `Content-Type` matching `^text/plain`. The streamed body is **not** matched in the pact: a text body is compared byte for byte, which would pin the cassette's prose. The conformance suite already proves the body parses as `PresentationModel` (AC-CONTRACT present check).
- **What the pact can't hold:** 401 and 429. The verifier's `requestFilter` sets a valid code on every replayed request (WU-22 note), so a "no code → 401" interaction can't verify, and quotas aren't reachable in one run. Those mappings are proven at unit + `msw` layers here and on the provider by the conformance `access` checks. Interaction 2 is the "first gated interaction" the WU-22 note asks for: its example code is not one the server accepts, so it passes only because the filter replaced it.
- **Runner:** a new Vitest project `contract-consumer` (`apps/**/*.pact.test.ts`, no network guard needed beyond loopback, excluded from `unit`). `scripts/run-contract.ts` runs it first, then the provider project, in both default and `--external` modes, so `pnpm test:contract` stays "consumer + provider" (§3). After the consumer run the runner checks the pact file is unchanged from git (`git diff --exit-code -- contracts/pacts`) **only when `CI` is set**, so a consumer change that wasn't committed with its pact fails CI the way `gen:check` does. Locally it just rewrites the file.

**D7. `@ai-sdk/react` not added yet.** The note asks to pin it at 4.0.158 (already in the catalog). Nothing in this unit imports it, and an unused dependency only adds audit surface; WU-14 adds it from the catalog. I'll add a Note to WU-14 so it isn't lost. *Alternative:* add it now as an unused dep. Small either way (Q3).

**D8. Functional tests (Playwright).** `webServer` runs `next build` then `next start --port 3000` with `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:4999` (nothing listens there; every API call is answered by `page.route` with fixtures built via `buildFixture`). Specs: shell renders with API "connected" (contract version shown), API "unavailable" (health 500 / network failure), each with an axe scan (§6.3). `reuseExistingServer: !process.env.CI`. CI gets `pnpm exec playwright install --with-deps chromium` before `pnpm verify` (WU-02 note); `--pass-with-no-tests` goes.

**D9. Browser pane launch config** (user request). `.claude/launch.json`, two configurations that call `node` directly on Next's bin (no `pnpm.cmd` shim, no shell, so it's Windows-safe):
```json
{ "name": "web", "runtimeExecutable": "node",
  "runtimeArgs": ["apps/web-nextjs/node_modules/next/dist/bin/next", "dev", "apps/web-nextjs", "--port", "3000"], "port": 3000 }
{ "name": "api", "runtimeExecutable": "node",
  "runtimeArgs": ["backends/api-nextjs/node_modules/next/dist/bin/next", "dev", "backends/api-nextjs", "--hostname", "127.0.0.1", "--port", "4000"], "port": 4000 }
```
During the build I'll start `web` (and `api` when showing the "connected" state) in the Browser pane to show you the shell. **Memory (3.9 GB):** before any gate step (`pnpm verify`, functional, contract) I stop both preview servers and close the pane; only one Next dev server plus the pane runs at a time unless I'm showing the connected state.

## 6. Risks & open questions

**Risks**
- **R1 — Pact replay may miss cassettes.** The verifier sends the pact's recorded JSON, which Pact may re-serialize (key order). The extract prompt serializes the *parsed* request (`dataBlock('currentProfile', …)` after Zod), whose key order follows the schema, so I expect hits. T2 proves it before anything is built on it. If it misses, the fix would be recording new cassettes, which costs money and needs your approval; I'll stop and ask (material deviation).
- **R2 — Coverage on `apps/*/src/**` (80%).** `layout.tsx`/`page.tsx` are included in coverage. I'll keep them thin and cover them with RTL unit tests rather than exclude them; if `layout.tsx` (renders `<html>`) can't be rendered sensibly in jsdom, I'll ask before adding any coverage exclusion.
- **R3 — Memory during `pnpm verify`.** The gate now builds two Next apps (web functional, api functional/contract), sequentially. Fine at 3.9 GB if nothing else runs; hence D9's stop-before-gate rule.
- **R4 — Pact on Windows** needs the VC++ runtime (already a README prerequisite) and runs the mock server on loopback, which the network guard allows.
- **R5 — shadcn CLI** may need network for its registry (D2 fallback: hand-written files from shadcn source).

**Questions**

## Deviations during implementation

1. **shadcn components written by hand (D2 fallback).** Planned: generate `button`, `card`, `badge` with the pinned shadcn CLI. Happened: wrote them from shadcn's new-york v4 source, with `components.json` kept so a later `shadcn add` lands in the same places. Why: the CLI installs its own dependency versions and edits `globals.css`, which would have fought the exact pins (§3). Not material.
2. **T2 spike result: Pact sorts JSON keys.** The verifier sends request bodies with keys in alphabetical order, not the order the consumer wrote. All four model-backed requests still replayed their existing cassettes (200s), because the prompt is built from the Zod-parsed request, whose key order follows the schema. R1 retired; no recording needed.
