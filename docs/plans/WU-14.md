## 1. Goal & scope

**Goal** (work breakdown): recommendations render progressively from the stream.

**In scope**
- The step from a `ready` profile to recommendations: a "Get recommendations" action, `POST /v1/trip/recommend`, then `POST /v1/trip/present` with what it returned.
- `useObject` from `@ai-sdk/react` 4.0.158 consuming the `/present` text stream, with a final schema check in `onFinish` (ADR 0001 Q7).
- Cards that render at every partial stage: missing keys, half-arrived cards and strings cut short.
- Verification badges per claim, held back until the card's blurb is complete (WU-11 note).
- Every failure on the way (before the stream and partway through it) gets a recoverable error state, with the invite-code flow on a 401.
- Unit tests for the partial-render components and view model, an msw integration test of the stream hook, and a Playwright streaming scenario with axe checks on every new page state.

**Out of scope**
- Journeys (WU-15).
- Any change to the HTTP contract, the backend or the pact. The pact already covers `/recommend` and `/present` (WU-12). Only the message catalog gains labels, if Q1 is answered yes.
- Showing the critic's unresolved issue text (Q2), booking links, maps and images.
- A claim's `kind` (flight, lodging, …): the statement already says it, and showing it would need more catalog labels.

## 2. Approach and key decisions

**D1. The conversation reducer gets a `trip` sub-state; it stays one store.** Per the WU-13 note, `reducer.ts` is extended rather than adding a second store:

```ts
trip:
  | { step: 'none' }                                  // not asked yet, or invalidated
  | { step: 'recommending'; request: RecommendRequest }
  | { step: 'presenting'; recommend: RecommendResponse; request: PresentRequest }
  | { step: 'presented'; recommend: RecommendResponse; model: PresentationModel }
  | { step: 'failed'; failedStep: 'recommend' | 'present'; error: ApiError; /* + what Retry resends */ }
```

New actions: `recommendRequested`, `recommendSucceeded`, `presentFinished`, `tripFailed`, `tripRetry`. The rules:
- `recommendRequested` is accepted only when `status === 'ready'` and no trip step is in flight.
- `presentFinished` is accepted only during `presenting`. A result from an aborted step is dropped, as for turns.
- A new extract response (`succeeded`) sets `trip` back to `none`, because the results were for the old profile. When the new profile is `ready`, "Get recommendations" shows again.
- `canSend` is false while a trip step is in flight, so a correction can't race a stream.
- `reset` (Start over) clears the trip. The hook aborts the request, and `useObject`'s `stop()` ends the stream.
- A 401 during a trip step uses the existing invite flow. `invite` becomes `asking` or `rejected`, and `inviteSubmitted` resends whichever step failed: the pending turn, or the trip step.
- Retry after a `present` failure resends only `/present`, with the same body. It doesn't call `/recommend` again, which would spend that endpoint's quota.

The partial object being streamed is the one exception to "one store". It lives in `useObject`'s state while the stream runs, as transient view data, and only the validated final object enters the reducer. *Rejected:* dispatching every partial into the reducer. That means re-implementing `useObject` with `parsePartialJson` from `ai`, against the work breakdown's scope ("`useObject`").

**D2. `useObject` sends through the typed client with a custom `fetch`.** `use-presentation.ts` passes `useObject({ api: '/v1/trip/present', schema: PresentationModel, fetch })`. Its `fetch` parses the body back to a `PresentRequest`, calls `client.present(body, { signal })`, and returns `new Response(stream)` when the result is 2xx. Otherwise it throws a `PresentFailed` error that carries the client's `ApiError`. Then the base URL, the bearer code and the status→`ApiError` mapping stay in one place, `client.ts` (WU-12 note).
- `onError` unwraps a `PresentFailed`.
- Any other error means the stream broke after a 2xx (`pipeTo` rejects; AC-PRESENT-08). It maps to a new `ApiError` kind, `{ kind: 'interrupted' }`.
- `onFinish({ object, error })` dispatches `presentFinished` with the validated object, or a failure of kind `contract` when the final value doesn't match the schema.
- An abort is swallowed by `useObject` itself.

*Rejected:* `useObject`'s own fetch with `api` + `headers`. It throws `new Error(responseText)` on a non-2xx, so the UI would have to parse error text, and the invite code and base URL would be read in a second place. *Rejected:* `@ai-sdk/react`'s `experimental_useObject`, a deprecated alias.

**D3. A pure view model decides what a partial card shows.** `src/lib/presentation/view-model.ts`: `presentationView(partial: DeepPartial<PresentationModel> | undefined, { finished }): PresentationView`.
- It keeps only fields that are strings, or arrays of strings, at the moment. A card with no `recommendationId` yet is skipped.
- Strings are shown as received, so `"Calm tur"` shows as `Calm tur` (ADR 0001 Q7). A screen-reader user isn't sent every token, because the cards are not a live region (D6).
- **Badges are held** until the card's blurb is done (WU-11 note): its `highlights` key has arrived, a later card exists, or the stream has finished. Until then the claims aren't shown at all, so a claim never appears without its label.
- A claim is shown only once its `statement` and `verification` are both present. After the hold that is always the case, because claims arrive before the title.

The DoD test feeds the view model **every prefix** of a fixture's final JSON text, parsed with `ai`'s `parsePartialJson`, the parser `useObject` uses. For each prefix it renders `PresentationCards` and asserts that nothing throws, and that no claim is shown before its card's blurb is complete. `ai` becomes a dev dependency of the web app, for tests only.

**D4. Badge wording.** "Unverified" and "From sample route data", plus one note above the cards:

> There's no live flight or hotel data here. Claims marked Unverified are the planner's suggestions; check them before booking. From sample route data means the route is in a small sample dataset, not a live schedule.

"Fixture" is jargon, so the badge doesn't use it. Where the words live is Q1.

**D5. Getting recommendations is an explicit action.** The ready turn keeps the composer for corrections (WU-13). Below the conversation, a **Get recommendations** button appears when `status === 'ready'` and `trip.step` is `none`.
- It posts `{ profile, referenceDate: today() }` to `/recommend`. On success it posts `{ profile, recommendations }` to `/present`: the response's recommendations unchanged and in order.
- *Rejected:* calling `/recommend` automatically on `ready`. Each call spends quota from a per-endpoint lifetime budget (ADR 0005), and a user often corrects one more detail first.
- With zero recommendations, `/present` still runs. The server writes a fixed headline and intro with `cards: []` (AC-PRESENT-13), and the UI adds "No trips matched this profile. Try changing a detail."

**D6. Accessible structure.** The results are a `<section aria-labelledby>`, with the stream's headline as its `h2` (or a hidden "Recommendations" heading until the headline arrives). The intro is a `<p>`, and the cards are an `<ol>` of `<article>`s with an `h3` title.
- The list has `aria-busy="true"` while the stream runs, so assistive tech doesn't read half-written text.
- One `role="status"` region is always in the DOM, and only its text changes (WU-13 note): "Finding trips…" while recommending, "Writing up your trips…" while presenting, "Your recommendations are ready." when done, and empty otherwise.
- Badges are shadcn `Badge`s, with text that holds AA contrast in both variants (checked by axe).
- There's no spinner or looping animation, so the axe helper's wait for animations still ends (WU-13 note).
- All model text renders as text nodes, never as HTML or markdown (WU-13 D3).

**D7. Errors reuse `ErrorNotice` and `error-text.ts`.** The trip step's error shows in the results area, using the same copy table as the conversation. Two kinds are new:
- `interrupted`: "The suggestions stopped partway." / "Try again." Retry is offered.
- A final object that fails the schema maps to the existing `contract` kind.

**Partial cards are discarded** when a stream fails. They were never validated, and their badges may never have shown, so leaving them up would present unlabelled claims (D3). *Alternative:* keep them dimmed under the error; see Q3.

**D8. Critic leftovers (Q2).** When `critique.unresolved` is non-empty, a short note above the cards says: "The planner's own checks still had concerns about these suggestions, so treat them with extra care." The issue text is model-written diagnostics, so it isn't listed.

**D9. Playwright streams for real through a local stream server.** `page.route` + `fulfill` sends a body in one piece, which can't show a partial stage or a transport error. So `tests/support/stream-server.ts` starts a Node HTTP server on a random port inside the test process. It writes a scripted list of chunks, sends CORS headers for `http://localhost:3000`, and can pause at a gate the test releases. It can also end with `socket.destroy()`, so the stream breaks without a clean end.
- `mockApi` gets a new answer kind, `{ stream: StreamScript }`, which calls `route.continue({ url: <stream server URL> })`. Every other route stays as it is.
- T0 checks that `route.continue` to another host delivers chunks progressively in Chromium (R1).
- *Fallback if it doesn't:* the functional test checks the final render and pre-stream errors only, and the partial and mid-stream cases rest on the unit and msw tests. That counts as a material deviation, so I'd stop and tell you.

**D10. Dependencies.** Add `@ai-sdk/react` (`catalog:`, 4.0.158) to `apps/web-nextjs` dependencies, and `ai` (`catalog:`, 7.0.154) to its devDependencies, for `parsePartialJson` in tests. `pnpm why zod` must still show one version. `pnpm audit --prod` runs in `verify`.

## Deviations during implementation

1. **`usePresentation` hands out stable functions (not material).** Planned: the hook returns `useObject`'s `submit` and `clear`. Actual: `useObject` creates both again on every render, and the effect that starts the stream depends on them, so each render would have aborted and restarted the stream. The hook keeps the latest pair in a ref and returns stable wrappers.
2. **The mid-stream case in the integration test bypasses msw (not material).** Planned (§3): the msw test covers "mid-stream error → `interrupted`". Actual: msw's interceptor ends an errored response stream cleanly, unlike a real connection. A probe showed a plain `Response` (and our wrapper) passing the error on, while msw's `fetch` returned the cut-off text as a clean end. So that one case gives the real client a `fetch` whose body errors. Under msw, a cut-off clean end would surface as `contract` (still recoverable, with Retry). The browser case, a destroyed socket, is proven in Playwright.
3. **No separate `use-presentation.test.tsx` unit file (not material).** Planned (§3): `use-presentation.ts (+ test)`. Actual: the hook is covered by `use-conversation.test.tsx` (unit, real `useObject` over a fake client stream) and `tests/integration/use-presentation.test.tsx` (real client over msw). A third file would repeat them.
4. **The Playwright browser wasn't installed (not material).** The local Playwright cache (`%LOCALAPPDATA%\ms-playwright`) was empty, so T0 and T6 waited for your OK to download Chromium for the pinned `@playwright/test` 1.64.1. You approved, and T0 then confirmed D9:
   - `route.continue` to the stream server delivered 7 separate reads.
   - The `Authorization` preflight passed.
   - A destroyed socket made the browser's read fail.
   - A 9-second pause mid-stream stayed open.
5. **T6 done by Opus, not Sonnet (not material).** Once T0 had proven the stream server, the spec was short and closely tied to it. A subagent's cold start would have cost more than writing it. Two existing lookups changed with it:

   - Alerts are scoped to `main`, because Next's route announcer is also `role="alert"`.
6. **`use-conversation.ts` lands in commit 4, not 3 (not material).** It now composes `usePresentation`, which needs `@ai-sdk/react`, so it moves with the streaming commit. Commit 3 keeps the reducer, the error kind and the shared fixtures.
7. **T4's every-prefix test renders less often (not material; plan fix 4).**
   - The view model still runs on every code-point prefix.
   - Components are rendered when the parsed shape changes (a key or an item appears), at every 12th other distinct value, and at the final text. Rendering at every distinct value took over 60 s on this machine.
   - The test takes about 9 s.
8. **One more file in T1 (not material).** The first `pnpm verify` failed 4 tests, because the `MessageCatalog` valid samples in `packages/domain-schema/tests/support/samples.ts` (added in WU-13, fix 2) lacked the new `verification` group. The sample builder now includes it, and the file lands in commit 2.

(a) The results status line used `empty:hidden`, which sets `display: none` while it is empty, so some screen readers may miss its first announcement. It now uses `empty:sr-only`, which hides it visually but keeps the live region in the accessibility tree. WU-13's `message-thread.tsx` and `message-composer.tsx` use the same pattern and are left as they are. (b) `tests/functional/conversation.spec.ts` (the status lookup scoped to the Conversation region) moved from commit 5 to commit 4, the commit whose second status region made that change necessary.
10. **The mock answer is `{ continueTo: url }`, not `{ stream }` (not material; unit review P2 #2).** Planned (D9): a `{ stream }` answer kind in `mockApi`.
