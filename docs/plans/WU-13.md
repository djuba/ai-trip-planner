## 1. Goal & scope

**Goal** (work breakdown): a user can converse until their profile is `ready`.

**In scope**
- `docs/features/conversation-ui.md` with the acceptance criteria (`AC-CONV-xx`).
- A pure conversation-state reducer. The client owns the state and sends the current profile with every turn (CLAUDE.md §5 "stateless").
- A message thread, clarification prompts rendered from violation `code` + `params`, a profile summary panel, a message composer with a code-point counter.
- **A message catalog in `spec/` (D13):**
  - `spec/messages/en.json` holds ICU MessageFormat templates for the 8 rule codes, and display labels for the closed enums;
  - `spec/messages.md` is its source-of-truth document;
  - a Zod `MessageCatalog` schema becomes `spec/generated/MessageCatalog.schema.json`;
  - a consistency test checks that the catalog covers every code and enum value and uses only real params;
  - the web app renders the catalog;
  - CLAUDE.md §2, §4.1 and §4.2 are updated to match.
- Loading and error states for every `ApiError` kind, including the invite-code entry after a 401, invite links (`?invite=<code>`), 429 `RATE_LIMITED` with `Retry-After`, and 429 `QUOTA_EXHAUSTED`.
- Unit tests (reducer, view helpers, components) and Playwright functional tests with contract-validated `page.route` mocks and axe checks on every state.
- The work-breakdown Notes: `MAX_MESSAGE_LENGTH` counted with `codePointLength` (WU-17), `clarificationQuestion` as plain text and the profile replaced each turn (WU-09), `createApiClient` + `ApiResult` + `AbortSignal` + `mock-api.ts` (WU-12), the gate UX (WU-22), and the `pnpm dev` invite decision (Q1).

**Out of scope**
- Calling `/recommend` and `/present`, cards and verification badges (WU-14). When the profile is `ready`, this unit shows that it is ready and keeps the composer open for corrections; WU-14 adds the next step.
- Journeys (WU-15).
- Keeping the conversation across reloads. Only the invite code is kept, for the browser session (Q3).
- The web Dockerfile and hosting (moved to WU-23 by WU-12).
- **No change to the HTTP contract, the rules or the API.**
  - Messages stay off the wire (§4.5), so `backends/`, `contracts/` and `contractVersion` don't change (Q5).
  - Under `packages/domain-schema` and `spec/`, only the message catalog is added.
- **The backend's clarification prompt doesn't read the catalog yet,** and nothing controls which language the model writes `clarificationQuestion` in. Both need a prompt change and re-recorded cassettes; that's a Note for a later unit.
- **Only English.** Another language is one more file, `spec/messages/<locale>.json`, plus picking the locale in the client.
- **Not in the catalog:** error copy, UI text and layout stay in each client (D6, D7). Only what every client must say the same way goes in the catalog.

## 2. Approach and key decisions

**D1. A pure reducer plus one hook that runs turns.** `src/lib/conversation/reducer.ts` holds the state machine; `use-conversation.ts` is the only place that calls the API. The reducer is pure, so every transition is unit-tested without React or fetch (§6.3 web unit layer: "the conversation-state reducer").

```ts
type Turn =
  | { role: 'user'; id: string; text: string }
  | { role: 'assistant'; id: string; kind: 'clarification'; question: string; violations: RuleViolation[] }
  | { role: 'assistant'; id: string; kind: 'ready' };

interface ConversationState {
  turns: Turn[];
  profile: TripProfile | undefined;        // replaced wholesale from each response (WU-09 note)
  status: 'idle' | 'sending' | 'needs_clarification' | 'ready';  // 'idle' = nothing sent yet
  pending: ExtractRequest | undefined;     // the request in flight or to retry; never lost on error
  error: ApiError | undefined;             // the last failure, until the next send or reset
  invite: 'none' | 'asking' | 'rejected';  // code entry shown only after a 401 (WU-22 note)
  nextId: number;                          // ids from the state, not Math.random (§6.1)
}
type Action =
  | { type: 'send'; request: ExtractRequest }
  | { type: 'succeeded'; response: ExtractResponse }
  | { type: 'failed'; error: ApiError }
  | { type: 'retry' }                      // re-sends `pending` unchanged
  | { type: 'inviteSubmitted' }            // after the code is stored; triggers a retry
  | { type: 'reset' };
```

- `send` adds the user turn, sets `pending`, clears `error`. The request is built by the hook: `{ message: text, currentProfile: state.profile, referenceDate }`, with `currentProfile` omitted on the first turn. Leading/trailing whitespace is kept as typed (the server and model handle it); only a blank message is refused (D4).
- `succeeded` replaces `profile` with `response.profile` (never merges), appends an assistant turn and sets `status` from `response.status`.
- **`failed` keeps the user turn and `pending`,** so Retry sends **the same request**, with the same `currentProfile`, and doesn't add a second user turn.
  - `status` goes back to what it was before the send (`idle`, `needs_clarification` or `ready`), so the composer is enabled again (review fix 1).
  - `aborted` is ignored, because that turn was replaced by a newer one.
  - `unauthorized` sets `invite` to `asking` when no code is stored. When a code is already stored (from `?invite=`, an earlier entry or this session), it goes straight to `rejected`.
  - To make that possible, `failed` carries `hadInviteCode: boolean`, which the hook reads from the invite store when the request is sent.
- The hook passes an `AbortSignal` per turn and aborts it on `reset` and unmount (WU-12 note).
- *Rejected:* a state library (Zustand, XState): one screen, a dozen transitions, and `useReducer` is testable as a plain function. *Rejected:* optimistic retries on `rate_limited`/`upstream`: the user decides when to retry, so a broken upstream never turns into a request storm against the quota.

**D2. `referenceDate` is the client's local date, injected.** `localDate(now: Date): string` formats `YYYY-MM-DD` from local fields (not `toISOString`, which is UTC and would give tomorrow's date in the evening in the Americas). The hook takes `today: () => string`, defaulting to `() => localDate(new Date())` at the component edge, so no tested logic reads the clock (§6.1, §4.6). Playwright fixes the date with `page.clock.setFixedTime`, which sets `Date` without faking timers, so hydration and React scheduling aren't affected (review fix 2). If even that misbehaves, the test computes the expected `referenceDate` in the browser instead.

**D3. Everything the model or user wrote is rendered as text.** `clarificationQuestion` is model-written (WU-09 note), so it goes into a text node, never `dangerouslySetInnerHTML` or markdown. **Violations:**
- They are rendered from `code` + `params` through the spec's message catalog (D13). `violation-text.ts` exports `describeViolation(v)`, which formats `catalog.violations[v.code]` with `v.params` using `intl-messageformat`.
- The ICU template carries the wording. For example `CHILD_AGE_RANGE` would be "A child's age must be between {min} and {max}. You said {age}.", and `INSUFFICIENT_DETAIL` would be "I need at least {required} details to plan a trip, such as where, when or who is going. So far I have {populated}." The exact wording is settled in T8.
- The UI shows the question first. Under it comes a short "What needs fixing" list, so the violations read as a checklist rather than a second paragraph saying the same thing.

**Plain text only.** Text never comes from `error.message`, and the UI never branches on the server's question (§4.5). The formatted string goes into a text node. ICU's rich-text tags are not used, so no template can inject markup.

**D4. The message cap is counted in code points; no HTML `maxlength`.** WU-17's note supersedes the earlier "set `maxlength`" note: HTML `maxlength` counts UTF-16 units and would stop a message of emoji at half the cap. The composer shows "N characters left" from `MAX_MESSAGE_LENGTH - codePointLength(text)`, marks the field `aria-invalid` and disables Send when over the cap or blank, and explains why next to the field (`aria-describedby`). The counter is not a live region (it would announce every keystroke); the over-cap message is. A 413 or 422 still gets an error state (AC-CONV-12), but an honest user never sees one. *Rejected:* truncating input as the user types (silently loses pasted text).

**D5. Invite code: asked for only after a 401, kept for the browser session.** `src/lib/invite.ts` wraps `sessionStorage` (key `vp.inviteCode`) in `try/catch`, falling back to memory when storage throws (private mode). `getInviteCode` reads it on every call, so a code entered after a 401 applies to the retry with no new client (WU-12 note). On mount, `?invite=<code>` is stored and removed from the address bar with `history.replaceState`, keeping any other query parameters and the hash. The entry form appears in place of the composer: It says "This planner needs an invite code" after a 401 when no code is stored. It says "That code isn't valid. Check it and try again." after a 401 when a code is stored, whether it came from an invite link, an earlier entry or this session (D1). Submitting stores the trimmed code and retries the pending turn. The code input is `type="text"` with `autocomplete="off"` and `spellcheck={false}`, not a password field: it is an invite, not a credential the user owns, and it must be checkable by eye.

**D6. One copy table for errors.** `error-text.ts` maps each `ApiError` kind to `{ title, detail, canRetry }`:

| kind | Shown | Retry |
|---|---|---|
| `rate_limited` | "Too many requests. Try again in about N minutes." (seconds under 60 shown as seconds, rounded up; `null` → "Try again in a little while.") | yes |
| `quota_exhausted` | "This invite has been used up." (no "try again", WU-22 note) | no |
| `message_too_long` | "That message is too long to send." | no (edit the message) |
| `upstream` | "The planner couldn't answer just now." (`refusal: true`: "The planner couldn't help with that request. Try rewording it.") | yes |
| `network` | "Can't reach the planner. Check your connection." | yes |
| `server`, `contract`, `invalid_request` | "Something went wrong on our side." | yes |
| `unauthorized` | handled by D5, not this table | — |
| `aborted` | nothing | — |

The error renders as `role="alert"` above the composer. Retry is a button; there is no automatic retry or countdown (D1).

**D7. Layout.** `page.tsx` keeps the header and footer and replaces the placeholder card with `<Conversation />` (a client component). On wide screens the thread and composer sit left and the profile panel right; on narrow screens the panel stacks above the composer. Accessible structure: the thread is `role="log"` with `aria-live="polite"` and a visually hidden heading; the loading indicator is a `role="status"` "Planning…" inside the conversation; the profile panel is a `<section aria-labelledby>` with a definition list. Tailwind + shadcn/ui only, no inline `style` (§9). New shadcn primitives are hand-added from shadcn's source with no new dependencies: `textarea`, `input`, `alert`; labels are plain `<label>` elements (shadcn's `label` would add `@radix-ui/react-label`).

**D8. Profile summary.** `profile-summary.ts` turns a `TripProfile` into rows `{ field, label, value, needsAttention }` in a fixed order (From, When, Where, Climate, Experiences, Also asked for, Travelers). `needsAttention` is true when a violation's JSON Pointer `path` starts with that field's pointer (`/people/1/age` marks Travelers; `""`, from `INSUFFICIENT_DETAIL`, marks nothing). Enum values (experiences, climate, travel mode, traveler type) are shown with their labels from the catalog (D13): `go-karts` → "Go-karts". Field labels and the rest of the panel's text are UI text and stay in the web app. Before the first response the panel says "Nothing yet. Describe your trip to get started." Dates show as given (`2030-02-10 to 2030-02-17`; flexible: "February 2030, 7 nights"), never parsed into `Date` objects. Strings from the profile render as text (D3).

**D9. Playwright mock answers in sequence, and requests recorded.** The clarification loop sends `POST /v1/trip/extract` twice with different answers, and the tests must check what the client sent. `tests/support/mock-api.ts` gains, backward-compatibly: an answer may be an array (consumed in order; running past the end fails the test like an unmocked request), and `mockApi` returns `{ requests }`, the parsed JSON bodies per key. New fixtures in `tests/support/fixtures.ts` are built with `buildFixture` (§6.1): a clarification for an invalid child age, a flexible-date profile, a ready response after a clarification.

**D10. Existing shell tests scope their status lookup to the footer.** The conversation adds a second `role="status"` (loading), so `getByRole('status')` in `shell.spec.ts` and `page.test.tsx` becomes `getByRole('contentinfo').getByRole('status')`. Their assertions don't change.

**D12. Fix the flaky axe scan that failed `verify` on `main` (added at your request before approval).** After the WU-12 merge (merge commit `d36ed42`, Actions run 43751467829), `verify` failed on `shell.spec.ts` "AC-WEB-12: shows the API as unavailable when it cannot be reached": it failed on the first try and on both retries. The same code passed on the PR. The cause is the timing of the axe scan. `badge.tsx` (shadcn) has `transition-[color,box-shadow]`. When the health request is aborted, the badge switches from outline ("Checking the API…") to destructive ("API unavailable") just before the scan, so axe reads text colours partway through the fade (#e8e8e8 and #f6f6f6 on #e7000b, contrast 3.89 and 4.41, under 4.5). The final white on #e7000b is about 4.7 (calculated, not measured). The fix changes only tests; the badge is unchanged:
- The scan helper moves from `shell.spec.ts` to `tests/support/axe.ts` (`expectNoAxeViolations(page)`), and `conversation.spec.ts` reuses it. That matters more in this unit, where every state change (loading, alert, invite entry) is scanned.
- Before it calls `analyze()`, the helper waits until no animation or transition is running: `await page.waitForFunction(() => document.getAnimations().every((a) => a.playState !== 'running'))`.
- It also calls `page.emulateMedia({ reducedMotion: 'reduce' })` first, as a backstop only. Tailwind's `transition-*` utilities don't respect `prefers-reduced-motion`, so the wait is what fixes the flake.
- The scan is not weakened: no axe rule is disabled, and every scan still covers the whole page.

*Rejected:* removing the badge's transition (a product change made to suit a test), and disabling `color-contrast` (would hide real failures). The same commit scopes `shell.spec.ts`'s status lookup to the footer (D10). That is harmless before the conversation exists, and it means `shell.spec.ts` lands in one commit and is already fixed before commit 4 adds a second `role="status"`.

**D13. The message catalog lives in `spec/`, beside the rules it describes (option D).** `spec/rules.md` holds what each rule means, `spec/fixtures/` holds its examples, and `spec/messages/` now holds how a client says it. Every client reads these as plain files, as CLAUDE.md §4 already requires for the rest of `spec/`. The backlog's mobile client, or a client in any other language, reads the same file.

**What changes**
- **`spec/messages/en.json`** is hand-written source of truth, like `rules.md`, and is not generated:
  ```jsonc
  {
    "locale": "en",
    "violations": { "CHILD_AGE_RANGE": "…{min}…{max}…{age}…", /* one per RuleCode */ },
    "labels": {
      "experience": { "beach": "Beach", "go-karts": "Go-karts", /* one per Experience */ },
      "climate":    { /* one per Climate */ },
      "travelMode": { /* one per TravelMode */ },
      "userType":   { "adult": "Adult", "child": "Child" }
    }
  }
  ```
- **`spec/messages.md`** is the source-of-truth document. It covers:
  - the file layout and the locale naming (BCP 47, one file per locale);
  - the template syntax: ICU MessageFormat, limited to simple arguments, `plural` and `select`, with no rich-text tags;
  - that the arguments are exactly the code's `params`, as defined in `rules.md` and `RuleViolation.schema.json`;
  - that a client may show a raw param value (for example a `YYYY-MM` string) as it is;
  - that messages are presentation only: never sent on the wire, never used for branching, with meaning still in `rules.md` (§4.5).
- **The catalog's shape gets a schema.** A Zod schema, `MessageCatalog`, lives in `packages/domain-schema/src/messages/catalog-schema.ts`. Its keys are typed from `RuleCode` and the enums, so a missing key fails `tsc`. `gen` writes it to `spec/generated/MessageCatalog.schema.json`, so a non-TS client can validate the file. It is not in `openapi.yaml`, because it never crosses HTTP.
- **A consistency test,** `src/messages/catalog.test.ts`, mirrors the existing rules `catalog.test.ts`. For each `spec/messages/*.json` it checks:
  - the file passes `MessageCatalog.schema.json` (Ajv);
  - every `RuleCode` and every enum value has an entry, and there are no extra keys;
  - every template parses as ICU (`@formatjs/icu-messageformat-parser`);
  - every argument a template uses is a property of that code's `params` in `RuleViolation.schema.json`;
  - the parser finds no tag elements.
  
  So adding a rule code or an enum value, which is a `feat(domain-schema)`, fails the gate until the catalog has its text.
- **New export `"./messages"`** (`src/messages/index.ts`) gives TS readers the catalog as typed data. It imports `spec/messages/en.json` and checks it with `MessageCatalog.parse` at load, so a broken file fails at once. The web app may import it. It is plain data, so it isn't `rules`, and the lint restrictions in §4.2 don't block it.
- **CLAUDE.md** gets three edits, in the same commit:
  - §4.1, Source of truth, gets a **Messages** bullet;
  - the §2 layout lists `spec/messages/`;
  - the §4.2 exports list `./messages`.
- **Web side:** `intl-messageformat` renders the templates, and `IntlMessageFormat` instances are cached per code. The locale is a constant `'en'` for now.
- **Dependencies:** `intl-messageformat` for the web app, and `@formatjs/icu-messageformat-parser` for domain-schema's dev tests. Both go into the pnpm catalog at exact versions (§3), choosing the newest release that clears `minimumReleaseAge`.

**Rejected alternatives**
- *Wording in the web app (option A):* every client would copy it, and the copies would drift.
- *A readable `message` on each violation in the response (option C):* this reverses §4.5, changes the contract, and puts the server in charge of the user's language.
- *Simple `{param}` substitution without ICU:* it can't do plurals, even in English ("1 detail" vs "2 details").
- *Generating the catalog from TS:* the wording is source material, like `rules.md`, not a shape. Generating it would make the TS package the source of truth for prose that non-TS clients need.

**D11. `pnpm dev` asks for the code, like the hosted app (Q1).** The dev API is configured with `local-dev-invite` (`.env.example`); the web app has no dev shortcut, so the first message in `pnpm dev` gets the 401 → code entry → retry, exactly as a recruiter would. Typing it once per browser session is the cost. *Rejected:* a `NEXT_PUBLIC_DEV_INVITE_CODE` variable: §5 says the frontend reads only `NEXT_PUBLIC_API_BASE_URL`, and it would hide the gate UX locally. A `?invite=local-dev-invite` link works in dev too, and the README's dev section says so.

## 6. Risks & open questions

**Answered:** Q1–Q4 (see "Decisions so far").

**Question for you**
- **Q5. Does adding the message catalog bump `contractVersion`?**
  - Recommended: **no**. `contractVersion` describes the HTTP contract (`GET /v1/health`), and no request or response changes.
  - The catalog is versioned with the repository. If a client ever needs to know which catalog it has, `spec/messages.md` can add a `catalogVersion` field later.
  - Alternative: a minor bump (0.8.0 → 0.9.0) to signal "the spec changed". But that changes `/health`, the pact and the cassette-backed conformance checks for no change in behaviour.

**Risks**
- **Next importing JSON from outside the app.** The web app imports `@vp/domain-schema/messages`, which imports `spec/messages/en.json`, a file outside the package. Turbopack's root is already the repo root (WU-12 D1), and `transpilePackages` covers the package, so it should resolve. T8's proof includes `pnpm --filter @vp/web-nextjs build`. If it doesn't resolve, the fallback is to have `gen` copy the catalog into the package as a generated module. That would be a deviation, recorded in the log.
- **The bundle size of `intl-messageformat`** (roughly 15–20 kB gzipped, with its parser). That's acceptable for a demo. The parse happens once per code, and the results are cached.
- **The ICU subset.** Clients in other languages need an ICU MessageFormat library. Those exist for Swift, Kotlin and Java (ICU4J), and `spec/messages.md` limits templates to features every one of them supports.
- **The clarification prompt and the catalog can disagree.** The model writes the question in its own words, while the checklist comes from the catalog. That's fine, because the checklist is the deterministic part. Unifying them is the later prompt change (out of scope).
- **Memory on this machine (~3.9 GB).** The Playwright run builds Next, so run the functional tests on their own, not alongside other gate steps.
- **Two `role="status"` regions** break the existing strict locators. D10 handles that, in commit 2.
- **`main` stays red** until this PR merges (D12). Any other PR opened meanwhile can hit the same flake. WU-15's journeys should reuse the `getAnimations` wait (a Note at close).
- **`getAnimations()` and infinite animations.** A looping animation never stops running, so the wait would time out. The loading indicator is text ("Planning…"), not a spinner. If a spinner is added, the helper must skip infinite animations (`effect.getTiming().iterations === Infinity`).
- **jsdom.** `history.replaceState` and `sessionStorage` work in jsdom, and the storage-failure path is tested by stubbing a `Storage` that throws.
- **Coverage.**
  - Web `src` must stay at ≥ 80%.
  - `packages/domain-schema/src/**`, which now includes `src/messages/`, must stay at ≥ 95% lines and branches.
  - The reducer and the helpers aim for about 100%.
