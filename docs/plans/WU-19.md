## 2. Approach & key decisions

**D1. Order: the hook-test fix first.** Every push in this unit runs `pnpm verify` from the `pre-push` hook, which runs `git-hooks.test.ts`. The 2026-11-10 incident came from that test inheriting `GIT_DIR` from a worktree's hook. This checkout is not a worktree, and earlier units pushed from it safely, but fixing the test first (CP1) removes the risk for every later push.

**D2. Strip `GIT_*` from every child process in the test, not just `git`.** The test also runs `gitleaks git --staged` and `pnpm exec commitlint`, and both read git state. One `childEnv()` helper in the test file returns `process.env` without any key matching `/^GIT_/i` (case-insensitive, because Windows env keys are), and `run()` passes it to every `spawnSync`. Rejected: deleting the variables from `process.env` at file load. That mutates the Vitest worker for other files and hides the dependency.

**D3. The isolation test is self-contained.** It lives in its own `describe`, outside the gitleaks `describe` whose `beforeEach` runs `git init` (plan review #1). The test first stubs `GIT_DIR` and `GIT_INDEX_FILE` (`vi.stubEnv`) to point at a separate sentinel repo, then runs its own `git init`, `git add` and gitleaks scan in the throwaway repo; `afterEach` calls `vi.unstubAllEnvs()`. It asserts that gitleaks found the staged secret (so it scanned the throwaway repo, since the sentinel has nothing staged), and that the sentinel is untouched: `core.bare` still `false`, `git ls-files` empty, no `config.ts` in its tree. It must fail before the fix, and that red run must show the sentinel's `core.bare` flipping to `true`, not only a staged file (checked by running it against the unfixed `run()` first). Rejected: stubbing for the whole file plus a final "untouched" test, which depends on test order.

**D4. Remove `backend` without a replacement field.** With one implementation it identifies nothing (work breakdown). `HealthResponse` becomes `{ status: 'ok', contractVersion }`. `BackendName` goes from `enums.ts` and the registry, so `gen` deletes `spec/generated/BackendName.schema.json` itself (`writeGenerated` removes stale files) and drops it from `openapi.yaml`.

**D5. `contractVersion` 0.2.0 → 0.3.0.** The contract is pre-1.0, so under semver a breaking change bumps the minor version. CLAUDE.md §4.3/§10 require a bump but don't say which part; this follows the precedent of 0.1.0 → 0.2.0 for an additive change, and is recorded in ADR 0003. (Q3.)

**D6. `HealthResponse` stays non-strict.** Like every other wire schema it has no `additionalProperties: false`, so a server still sending `backend` would pass the schema. The conformance suite stays tolerant of extra fields on purpose (§6.5: check only what §5 specifies). Absence is proven where it is cheap: api-nextjs's integration and functional health tests compare the whole body with `toEqual`, and a unit test in `schemas.test.ts` pins `HealthResponse`'s keys to `['status', 'contractVersion']`.

**D7. CLAUDE.md is changed in two places, each with what it governs.** §10's scope list and `scripts/commitlint-config.test.ts` must change together (that test says so), so §10, §2 and §9 go with the removals in CP3. §5's health row goes with the contract change in CP2. The reframing (§1, §4, §6.5–§6.7, title) goes with ADR 0003 in CP4.

**D8. Wording.** ADR 0003 names the patterns precisely: Specification by Example (executable specification, the idea under BDD, not full BDD with Gherkin written with the business); shared test vectors; spec-first (contract-first) API design; consumer-driven contracts; ports and adapters. The README describes the project as it is, without the removal history (that lives in ADR 0003). CLAUDE.md §6.5's rule-parity paragraph becomes the plain test: every `spec/fixtures/rules` case goes through `/extract` with a mock `LlmClient`; the normalized profile is unchanged and violations compare exactly and in order. Nothing about JUnit reports or `RULE-FIXTURE` titles.

**D9. Product name "AI Trip Planner"**, matching the new repo name (Q1). It replaces "AI Vacation Planner" in the README title, CLAUDE.md title and §1. The `@vp/*` scope stays (Q4).

**D10. The repo rename is the last code checkpoint (CP5),** so every earlier push goes to the current URL, and the rename touches only names. At CP5 I ask before running `gh repo rename ai-trip-planner` (outward-facing). Then `git remote set-url origin https://github.com/djuba/ai-trip-planner.git`. GitHub carries the branch protection, the required `verify` check and the open draft PR across a rename, and redirects old URLs, so the PR links in done WU sections are left as they are.
