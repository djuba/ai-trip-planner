## 1. Goal & scope

**Goal** (work breakdown): a reviewer understands the design in five minutes and can run it in ten.

**In scope**
- `README.md`, reorganized for a reviewer: what it is, a quickstart, an architecture diagram, the AI pipeline, the design and tradeoffs (the WU-19 section, plus hosting from ADR 0005), the test pyramid and how to run each gate, and the cost-control approach.
- Contract docs: a README section that names the endpoints, links `spec/generated/openapi.yaml` and says what each file in `spec/` is for.
- A decision records index, `docs/decisions/README.md`.
- The two Notes on this unit: the "How the design is checked" table loses its Status column (every row is Built), and the gate set is described as it now stands (project, integrated, full, CI `image` and `infra`, the post-deploy contract check). The hosting approach is covered as a design decision, with no link to the hosted environment (WU-23 adds the "live demo on request" line).

**Out of scope**
- Any change to code, the contract, tests (other than the doc check in D5), CI or `CLAUDE.md`.
- A live demo, or any link to the hosted environment (WU-23).
- Generated API reference pages (e.g. Redoc). `openapi.yaml` renders on GitHub as text and any OpenAPI viewer can open it; a docs site is not worth the build step.

## 2. Approach and key decisions

**D1. "A working UI in replay mode" means watching the journeys, not `pnpm dev`.** Replay answers only requests that were recorded, and every cassette key includes the request's `referenceDate`, the browser's local date. So `pnpm dev` in replay mode works for nobody: anything a person types misses its cassette, and even a recorded message misses on any day but 2026-11-16. The journeys fix the browser clock and type the recorded messages, so they are the replay-mode UI. The quickstart's last step is `pnpm test:journeys --grep @smoke --headed` (a visible browser runs the clarification-to-recommendations journey) or `--ui` (Playwright's UI mode, to step through it with DOM snapshots). Both pass through the runner unchanged (`scripts/run-journeys.ts`). The README then says plainly how to try your own messages: `pnpm dev` with `LLM_MODE=live` and your own `ANTHROPIC_API_KEY`, which costs money.
*Rejected:* a build-time reference-date override in the web app (`NEXT_PUBLIC_REFERENCE_DATE`) for a "demo" build. It would let a person click through recorded messages by hand, but it adds a dev-only path to the client for a docs unit, and still fails on any message not recorded. Open question Q1.

**D2. The README is the five-minute read; detail stays where it lives.** It links to the ADRs, feature docs, `CLAUDE.md` and `infra/README.md` rather than repeating them. Order: pitch → quickstart → architecture → pipeline → design and tradeoffs → testing and gates → cost control → the contract → where to find things → documentation. The existing sections that still hold (pipeline, design and tradeoffs, patterns, "How the design is checked", where to find things, Clean Architecture mapping, where tests live) are kept and edited, not rewritten: they were reviewed in WU-19.

**D3. Diagrams in Mermaid.** GitHub renders Mermaid in Markdown, so the diagram is text, diffs cleanly and needs no image tooling. One flowchart: browser → `web-nextjs` → HTTP (`/v1`, invite code) → `api-nextjs` (route handlers → use cases → `LlmClient` → AI SDK → Anthropic, or cassettes in replay), with `spec/` feeding the schemas, the client, and the provider contract tests that hit the API over HTTP. The test pyramid is a table, top (journeys, few) to bottom (unit, hundreds), with what each layer proves and fakes (CLAUDE.md §6.3); Mermaid has no pyramid shape, and a drawn one says less than the table. No test counts: they would drift.

**D4. Gates table as they now stand** (CLAUDE.md §6.7): pre-commit, `pnpm verify`, `pnpm verify:integrated`, `pnpm verify:full`, CI `verify` / `image` / `infra` (the three required checks), and the deploy workflow's post-deploy contract check. One row each: command, what it runs, where it runs.

**D5. A unit test keeps the docs from rotting.** `scripts/docs-links.test.ts` (unit project, already globbed by `**/*.test.{ts,tsx}`) checks that every relative link in `README.md` and `docs/decisions/README.md` resolves to a file in the repo (anchors ignored), and that every `docs/decisions/NNNN-*.md` appears in the index. WU-23 and later units edit the README, and a renamed file breaks a link silently otherwise. It reads files only, no network. Open question Q2.

**D6. Cost control in one section.** Development: `LLM_MODE` replay/mock for every gated test, a cassette miss fails instead of going live, `pnpm eval --budget`, model tiering (`MODEL_FAST` for extraction and presentation), `effort` and `maxOutputTokens` per stage, byte-stable system prompts for prompt caching, and per-call usage logging. Hosted (ADR 0005): scale to zero on Cloud Run, replay mode until WU-23, invite codes with per-endpoint quotas, hourly and daily windows, and the $5–10 monthly budget. Nothing is claimed about the live demo's spend limit, which WU-23 sets up.

**D7. The DoD is proven on a real fresh clone.** After the README is written, the main agent clones the branch tip into the scratchpad (`git clone --branch wu/WU-16-…`), follows only the README's quickstart (no `.env.local` carried over, no `node_modules`), and runs `pnpm verify` and the `--headed` journey there. Any step the README missed is fixed in the README and the check re-run. The result goes in the deviations section and the close commit's Notes.

## 6. Risks & open questions

- **Q1 — The replay-mode UI.** Is watching the journeys (`--headed` / `--ui`) what you want the DoD's "working UI in replay mode" to mean (D1)? *Recommended: yes.* The alternative is a demo build with a fixed reference date, which is an app change and would grow this unit.
- **Q2 — The doc-link test (D5).** *Recommended: yes*; it's small and protects every later README edit. Without it, links are checked once by hand in T2.
- **R1 — The fresh-clone check is slow.** `pnpm install` plus `pnpm verify` plus a journey build in a clean clone is likely 10–20 minutes. It runs in the background. The "ten minutes" in the goal is the reviewer's hands-on time, not the verify run; the README says how long the gate takes.
- **R2 — Chromium download.** A fresh clone needs `playwright install chromium` before `pnpm verify` (the web functional tests use it). The quickstart puts it right after `pnpm install`.
- **R3 — Prerequisites a reviewer may lack.** gitleaks matters only for committing, and Docker only for `pnpm test:image`; the quickstart marks both optional for running and verifying.

## Deviations during implementation

1. **The README's route-handler path was wrong** (not material). The old README, kept from WU-19, gave `backends/api-nextjs/app/v1/**/route.ts`; the handlers are in `backends/api-nextjs/src/app/v1/`. Fixed in both tables. Found by a one-off check that every concrete backticked path in the README exists (not committed: the link test covers links only).
2. **Mermaid checked in the browser pane, not with the Mermaid CLI** (not material). The diagram was rendered with `mermaid@11.4.1` from jsDelivr in the built-in browser; it parsed and laid out without errors. GitHub renders it on the PR once pushed.
3. **The fresh clone was a local clone of the branch** (not material). The README and index were uncommitted during the build, so D7 cloned the branch tip from the local repo and copied in the three new or changed files, with no `node_modules` and no `.env.local`. pnpm's content store on this machine was warm, so the install time is not representative of a first install.
4. **R1 did not happen** (not material). In the fresh clone, `pnpm verify` took about 30 seconds (2,830 unit and integration tests, 49 functional, 40 contract) and the headed `@smoke` journey about 8 seconds, builds included: Turbopack builds each app in under a second here. The README says the gate takes under a minute on a recent Mac, instead of the "several minutes" first drafted.
5. **A fix commit after the README commit** (not material). The unit review's two P2 findings on the link test were approved at the close commit, after the index commit was made, so they land fixed forward as `fix(repo): check heading anchors in doc links`: anchors are checked against GitHub's heading slugs (with the `-1` suffix for repeated headings), and fences indented inside list items are stripped. A sample test pins both. Checked by hand that a renamed anchor fails the test.
