## 2. Approach & key decisions

**D1. `LlmClient.streamObject` (§7, §9; WU-08 Note).** Added beside `generateObject`, with the same `LlmObjectRequest<T>`:

```ts
streamObject<T>(request: LlmObjectRequest<T>): Promise<AsyncIterable<LlmStreamPart<T>>>;

type LlmStreamPart<T> =
  | { type: 'partial'; partial: PartialObject<T> }
  | { type: 'final'; object: T }; // always the last part; passed `schema` and `accept`
```

`PartialObject<T>` is our own deep-partial type, so `src/usecases` still doesn't name the SDK. There is no separate `object` promise (review finding 1): a promise nobody awaits after a mid-stream failure would be an unhandled rejection, which can crash the server. The final object is the iterator's last part, and every failure surfaces in exactly one place, the iterator. A unit test proves a mid-stream failure leaves no unhandled rejection. The semantics:
- **Before the first output** (the returned promise): an upstream error, a refusal or a stream that ends with no output is handled exactly like `generateObject`: one retry, then `LlmError` (`LLM_UPSTREAM_ERROR` or `LLM_REFUSAL`). Nothing has reached the client yet, so it becomes a normal JSON 502. A cassette miss rejects as itself (a 500, as today).
- **After the first output** there is no retry: bytes have gone out. A failure (an `error` part, `finishReason` other than `stop`, or a final object that fails `schema` or `accept`) makes the iterator throw an `LlmError` with `midStream: true`.
- Every attempt logs one `LlmCallLog` line, as now, when it ends.

The adapter uses `streamText` + `Output.object`, the same provider options as `generateObject` (`outputFormat`, `maxRetries: 0`, `effort`, `maxOutputTokens`) and reads `fullStream` so that `error` and `finish` parts are seen, not just partials (ADR 0001 Q1, Q5). Which `fullStream` part types carry the partials in `ai 7.0.154` is checked against the pinned docs in T2.

Mock mode streams the same way: a `MockReply` is split into small chunks by the mock model's `doStream`, so mock tests exercise the real adapter. `mockStreamFailure(afterChars)` gives a mid-stream error.

Rejected: returning a `ReadableStream<string>` of model text from the client. It would push the wire format into `src/llm`, and the model's text is not the wire (D3).

**D2. Contract: `PresentationModel` capped on the wire, `PresentationCopy` for the model (ADR 0001 Q3, ADR 0004, §4.4–4.5).**
- New model-only schema `src/wire/llm/presentation-copy.ts`: `PresentationCopy { headline, intro, cards: [{ title, blurb, highlights: string[] }] }`, unconstrained. It has no ids and no claims: the model never writes them.
- `PresentationModel` becomes wire-only. `cards` is `.max(MAX_RECOMMENDATIONS)`, `recommendationId` uses `MAX_SHORT_TEXT_LENGTH`, and `claims` becomes `FactualClaim[]` `.max(MAX_CLAIMS)`, the capped wire claim (the private uncapped `PresentationClaim` goes).
- New constants (proposed values, Q2): `MAX_HEADLINE_LENGTH` 120, `MAX_INTRO_LENGTH` 600, `MAX_CARD_TITLE_LENGTH` 100, `MAX_BLURB_LENGTH` 600, `MAX_HIGHLIGHTS` 5, `MAX_HIGHLIGHT_LENGTH` 120. The prompt asks for about half of each, so a cap only bites on misbehaviour.
- Only a response narrows, so this is **not breaking**: `contractVersion` 0.7.0 → **0.8.0** as `feat(domain-schema):`. `spec/generated/` gains `PresentationCopy.schema.json` (not in `openapi.yaml`).

**D3. Code writes the JSON stream; the model's text is never passed through.** The model streams `PresentationCopy`. A new pure module, `src/usecases/present/stream-writer.ts`, turns its partial snapshots into the wire text:
- It renders the wire object in a fixed key order. In each card the code fields come first: `{"recommendationId":"rec-1","claims":[…],"title":"…`.
- For each snapshot it renders the **open prefix**: everything up to the field still being written, with no closing quotes or brackets. A field counts as complete once the next key in schema order exists, so out-of-order keys wait. It emits only what extends the text already sent. On the final object it closes every bracket.
- Strings and arrays only grow in a well-formed stream, so each prefix extends the last. A trailing lone high surrogate is held back until its pair arrives. A snapshot that wouldn't extend the sent text is skipped, never emitted (a unit test proves the output is always a prefix of the final text).
- Cards are **index-aligned** with `recommendations`. Model cards past the last recommendation are dropped. If the model writes fewer cards, code appends one for each missing recommendation from its own data (`title` = destination, `blurb` = summary, no highlights), so every recommendation gets a card and keeps its claims.
- The final text is `PresentationModel.safeParse`d on the server, too. A failure is logged as a bug signal; it can't be taken back.

The route serves it with `createTextStreamResponse({ stream })` over this string stream: `text/plain; charset=utf-8`, no framing.

Rejected: piping the model's own text through `toTextStream`, as CLAUDE.md §7 currently says. Then the model would have to write `recommendationId` and copy every claim, label included, which the WU-10 Note forbids, and no cap could be held. Also rejected: waiting for the whole object and sending it at once, which isn't a stream. **This changes CLAUDE.md §7's Present row and ADR 0001's Decision line** (Q1, approved); both are updated in commit 5, with the route that makes them true (review finding 5).

**D4. Caps while streaming: a string stops at its cap, on a word boundary, ending in "…" (Q3 (a), approved).** Streamed text can't be discarded after it's sent. So:
- In an open string the writer emits text only up to its last whitespace, holding back the word still being written; the word goes out once whitespace follows it or the string closes. A held word longer than 32 code points goes out anyway, so a long run with no spaces still streams.
- When a string would exceed its cap, the writer ends it at the last word boundary that leaves room for "…" (U+2026), and appends "…". The text it sends, "…" included, is at most the cap in code points. With no boundary in reach (a single held run) it cuts at cap − 1 and appends "…". The rest of the model's string is received and never sent, and one `Discarded`-style signal is logged (`reason: 'truncated'`, the path and the received length).
- Items past a count cap (`MAX_HIGHLIGHTS`, cards past the recommendations) are dropped whole, as ADR 0004 does.

So the final object always passes the wire schema. **ADR 0004 gets an addendum** (commit 2): the "discard, never truncate" rule applies to stored or forwarded values; streamed prose is the one exception, cut visibly with "…", because the alternative is buffering each string, which loses the streaming. Rejected: buffering each string until complete and replacing an over-cap one with code fallback text (option (b) in Q3).

**D5. Failures (§5, ADR 0001 Q7).**
- Before the first output: the normal JSON 502 (`LLM_UPSTREAM_ERROR` or `LLM_REFUSAL`) with CORS, from D1's promise. The route doesn't return its `Response` until the first snapshot is in.
- After it: the response stream is **errored**, not closed. The connection ends without the final chunk, so a client sees a transport error (`curl` exit 18; `useObject` an error) instead of a well-formed but cut-off body. The writer never closes the JSON on a failure.
- CLAUDE.md §5 gets one sentence on this (commit 5), and the `/present` description in `openapi.yaml` says the same (commit 2).
- **Proved over real HTTP** (review finding 2): a functional test boots the built app in replay mode against a hand-built cassette whose SSE stream sends some text and then `event: error`. It asserts a 200 with some body bytes, then a transport error on the client (the body read rejects), never a clean end. If Next turns an errored stream into a clean close, that is a material deviation: I stop and tell you before choosing another way to signal it.

**D6. Claims carried through unchanged, with the `fixture` label re-checked (WU-10 Note; Q4, approved; review finding 3).** `claims` come from the request, mapped by code. The request is client-supplied, so `/present` re-checks each `fixture` claim with the WU-10 rule itself: the claim keeps `fixture` only if it has `kind === 'flight'`, its structured route leaves from the traveler's **resolved origin** (from the request's profile, resolved the way `/recommend` resolves it), the route is in `routes.json`, and its statement equals the one the WU-10 builder writes for that route. Otherwise it is sent as `unverified`, statement unchanged. So the server never streams a `fixture` label it can't back. The route data is injected, as for `/recommend`, and the builder is reused, not copied.

**D7. The prompt (§8.3; WU-09 Note).** A constant system prompt with `DATA_BLOCK_RULE`. The user message holds the profile and the recommendations as data blocks, **without their claims**, so the model has no flight or price specifics to restate. The system prompt says: one card per recommendation in the given order; prose only; no flight, lodging, price or schedule specifics; never say anything is verified. It states the lengths to aim for (about half the caps).

**D8. Token budget.** `PRESENT_MAX_OUTPUT_TOKENS` in `token-budget.ts`, from the copy caps at 2 tokens per code point, as the other stages. Haiku at `effort: low`, so no thinking margin. Hitting it is a mid-stream failure (D5).

**D9. Route and runtime (WU-06, WU-09 Notes).** `src/http/present.ts` exports `createPresentPost({ llm, routes, logDiscarded })`, on the `createRecommendPost` pattern. In record mode `runtime.flush()` runs when the response stream ends or fails, not in a `finally` before returning. `route()` passes the streaming `Response` through unbuffered (AC-API-12). `OPTIONS = preflight` stays.

**D10. Recorder (WU-08 Note).** `cassette-fetch.ts` writes an SSE cassette only if the stream has a `message_stop` event and no `event: error`; otherwise it warns and writes nothing, like a non-2xx.

**D11. Eval (WU-18 Note; Q5).** `EvalCase` gains stage `present`. The runner calls the present use case with the case's profile and recommendations, and the observer wraps `streamObject` too. Cases plant instructions and a canary in recommendation strings (`destination`, `summary`, a claim statement). Scorers: the existing canary and leak scorers, plus a new one that every claim and label came out unchanged. One live run, compared with the WU-10 run in `runs.jsonl`, within US$5 (Q5).

**D12. No recommendations (review finding 4).** A request with `recommendations: []` makes no model call. Code streams a fixed headline and intro (constants in `prompts/present.ts`, saying no destinations matched) and `cards: []`. It still passes `PresentationModel`, and the stream has one chunk, which is fine for an empty result.

## 6. Risks & open questions

**Questions for the user**
- **Q1.** D3 serves code-written JSON instead of passing the model's text through `toTextStream`. That changes CLAUDE.md §7's Present row ("Serve with `createTextStreamResponse({ stream: toTextStream(…) })`") and ADR 0001's Decision. Approve the change? (Recommended: yes; it's the only way to keep ids and claims out of the model's hands and hold the caps.)
- **Q2.** Cap values in D2 (headline 120, intro 600, card title 100, blurb 600, 5 highlights of 120). Recommended as proposed.
- **Q3.** Over-cap streamed strings: (a) stop at the cap, logged, with an ADR 0004 addendum (recommended), or (b) buffer each string until complete and swap an over-cap one for code fallback text, keeping "never truncate" but losing per-character streaming.
- **Q4.** Re-check `fixture` labels on `/present` (D6)? Recommended: yes, small and keeps the server from streaming a label it can't back.
- **Q5.** Eval budget for the live run. Recommended: **US$5** (Haiku, a dozen cases × repeats).
- **Q6.** Hosted chunking (formerly R4): a `curl -N` check after the merge; any fix goes on a follow-up branch.

All six were answered on 2026-11-14; see the approval section at the top.

**Risks**
- **R1.** The partial-snapshot API of `streamText` in `ai 7.0.154` may differ from the docs I've read so far (`fullStream` part types, whether partials are deep-cloned). T2 checks the pinned docs first; a mismatch changes the adapter, not the interface.
- **R2.** The writer's prefix property depends on snapshots only growing. The skip-and-wait rule (D3) keeps it safe; unit tests cover escape sequences, surrogate pairs, out-of-order keys and shrinking snapshots.
- **R3.** Recording mid-stream failures live isn't possible, so AC-PRESENT-08 uses hand-built SSE cassettes and a mock stream (as AC-LLM-12 did).
- **R4.** Moved to Q6 (review finding 6).
- **R6.** Next may turn an errored response stream into a clean close (D5). The functional test catches it; if so, it is a material deviation and I stop before choosing another signal.
- **R5.** Contract cassettes are keyed on the model request. If T6's prompt changes after T9, re-record.
