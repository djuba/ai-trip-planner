# WU-04 — Contract wire schemas & generation: plan

**Status:** approved (2026-11-03) with the revisions in §9 · **Depends on:** WU-02 (done), WU-03 (done) · **Author:** main agent (Opus), 2026-11-03

## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): the language-neutral contract exists as Zod plus committed JSON Schema/OpenAPI artifacts.

**In scope**
- `packages/domain-schema/src/wire/`: `Experience`, `Climate`, `Traveler`, `DateRange`, `TripProfile`, `ExtractionSchema`, `RuleCode` + `RuleViolation`, `Recommendation` + `RecommendationSet`, `PresentationModel`, the request/response envelopes for all four endpoints, `ErrorResponse`.
- Constants `MIN_POPULATED_FIELDS` and `CONTRACT_VERSION`.
- A `gen` script that writes `generated/*.schema.json`, `generated/openapi.yaml` and `generated/constants.json`, plus a `--check` mode wired into `pnpm verify` as the drift check.
- The `exports` map (`./wire`, `./rules`) — already present from WU-01; kept and tested.
- `buildFixture(schema, value)`: the §6.1 helper that `safeParse`s every fixture/mock payload.
- Pinning the ADR 0001 versions in the pnpm `catalog:`.
- Decision on the open question shared with WU-05: where the flexible `month` 1–12 range is enforced (D6).

**Out of scope:** rule implementations, `rules.md`, `normalize`, `countPopulatedFields` and the `fixtures/` cases (WU-05); the backend-internal `CritiqueResult` and any stage-specific LLM sub-schemas other than `ExtractionSchema` (WU-10/WU-11 derive them); the conformance suite that consumes `generated/` (WU-07); generating Python/Go models (backlog).

## 2. Approach & key decisions

| # | Decision | Why / CLAUDE.md | Rejected alternative |
|---|---|---|---|
| D1 | **Anything a rule checks is not constrained in the wire schema.** `TripProfile` (and therefore `currentProfile`, `profile` in requests and responses) carries types and enums only: ages are `int`, not `0..120`; `fixed` dates are plain `string`, not `format: date`; flexible `month` is `int`, not `1..12`. Constraints go only on fields no rule covers (`referenceDate` is `z.iso.date()`, `message` is `min(1).max(2000)`). | §4.5: shape errors are 422, business problems are 200 + `needs_clarification`. A `needs_clarification` response must be able to *carry* the bad value (e.g. a child aged 18) and the client must be able to send it back next turn. If the wire schema rejected it, the server's own response would be non-conformant and the client's next request would 422. | Constraining the wire too (§4.1 allows it): it makes every rule violation a contract violation. |
| D2 | **Generated JSON Schema uses open objects** (no `additionalProperties: false`), emitted with `z.toJSONSchema(…, { io: 'input' })`. Zod objects stay the default strip mode. | Tolerant reader: matches what Zod, Pydantic and Go's `encoding/json` already do with unknown keys, so adding an optional response field never breaks an older client, and Zod/Ajv parity holds. Probed on zod 4.6.7: `io: 'output'` emits `additionalProperties: false`, `io: 'input'` omits it, nothing else differs for our constructs. | Strict objects: Zod would accept what the JSON Schema rejects (parity break), and every additive change becomes breaking. |
| D3 | **One file per named schema, cross-referenced by relative `$id`/`$ref`.** Every schema is registered in a dedicated `contractRegistry` (`z.registry<{ id; description? }>()`), not Zod's global registry. `gen` emits `z.toJSONSchema(contractRegistry, { uri: id => \`${id}.schema.json\` })` → `generated/<Id>.schema.json`, and a second emission with `uri: id => \`#/components/schemas/${id}\`` → `components.schemas` in `generated/openapi.yaml`. | §4.1: JSON Schema and OpenAPI generated from Zod; Python/Go generate from `generated/`. Per-file `$id`s are what `datamodel-code-generator` and Go generators consume. A private registry means nothing outside the contract can leak into `generated/`. | One bundled file with `$defs`: harder to diff and to validate one payload type at a time. |
| D4 | **`openapi.yaml` is OpenAPI 3.1.1**, built in code: `info.version = CONTRACT_VERSION`, the four §5 paths with request/response schemas, `200`/`422`/`502`/`500` responses referencing `ErrorResponse`, CORS not described. `/v1/trip/present` responds `text/plain` with a description saying the body is streamed JSON text that parses as `PresentationModel` (§5); its schema is referenced via `x-final-schema` since OpenAPI cannot type a partial stream. Serialised with `yaml` **2.9.1**. | §5; OpenAPI 3.1's schema dialect is JSON Schema 2020-12, which is zod's default target, so the same schemas are reused unchanged. | OpenAPI 3.0 (`target: 'openapi-3.0'`): nullable/`const` differences for no gain. |
| D5 | **`RuleViolation` = discriminated union on `code`, with typed `params` per code; `path` is a JSON Pointer string** (RFC 6901, e.g. `/people/2/age`, `""` for the whole profile). Params per code: `CHILD_AGE_RANGE {age, min, max}`, `ADULT_AGE_RANGE {age, min, max}`, `DATE_ORDER {start, end}`, `DATE_NOT_PAST {value, referenceDate}`, `DATE_VALID {value}` (`string \| int`), `PARTY_HAS_ADULT {}`, `INSUFFICIENT_DETAIL {populated, required}`. | §4.5: clients and the clarification prompt render text from `code` + `params`, so `params` must be typed per code to be renderable without guessing. JSON Pointer is language-neutral. No `record` (also an LLM hazard, ADR Q3), and the clarification stage may hand violations to the model as input. | `params: Record<string, unknown>`: untyped, and generators produce `dict[str, Any]`. Path as `(string\|number)[]`: fine too, but a pointer is one comparable string. WU-05 may still add codes (a `feat`), but changing params is breaking, so they are fixed here. |
| D6 | **Open question resolved (recommended): no new rule code; `DATE_VALID` also covers a flexible `month` outside 1–12.** Its `path` points at `/dateRange/month` and `params.value` is the number. CLAUDE.md §4.6 `DATE_VALID` row becomes "fixed `start`/`end` are real `YYYY-MM-DD` calendar dates, and a flexible `month` is 1–12". WU-05 implements it and writes it into `rules.md`. | A month of 13 is "not a real calendar date"; one code keeps the client's clarification copy simpler. ADR 0001 Q3 says the range cannot live on `ExtractionSchema`; D1 says it cannot live on the wire either. | A new `MONTH_RANGE` code: one more enum value and copy string for the same idea. **Needs your decision (Q1)** because it edits CLAUDE.md §4.6. |
| D7 | **`ExtractionSchema` and every schema a model fills use only ADR 0001 Q3 "use" constructs.** In WU-04 that is `ExtractionSchema`, `RecommendationSet` and `PresentationModel` (WU-10/11 may hand these to the model directly or derive sub-schemas). Every field is required; "absent" is `null`. `z.int()` is allowed: its emitted ±`MAX_SAFE_INTEGER` bounds are the only numeric constraints tolerated (the spike used `z.int()` live without issue). | §4.4 and ADR 0001 Q3. Making recommend/present LLM-safe now avoids a breaking contract change in WU-10/11. | Leaving recommend/present shapes free-form and constraining them later: likely a breaking change. |
| D8 | **Minimal, provisional recommend/present shapes** (pre-1.0, `CONTRACT_VERSION = '0.1.0'`): `Recommendation { id, destination, summary, matchedExperiences: Experience[], claims: FactualClaim[] }`; `FactualClaim { kind: 'flight'\|'lodging'\|'price'\|'activity'\|'other', statement, verification: 'unverified'\|'fixture' }`; `RecommendationSet { recommendations }` (what the model produces); `RecommendResponse { recommendations, critique: { pass, unresolved: CritiqueIssue[] } }` with `CritiqueIssue { recommendationId: string\|null, issue: string }`; `PresentationModel { headline, intro, cards: PresentationCard[] }` with `PresentationCard { recommendationId, title, blurb, highlights: string[], claims: FactualClaim[] }`. No numeric price fields. | §7 factual honesty: every claim carries `verification`, and invented prices aren't modelled as data. §7 stage 3: `recommendationId` and `claims` are code-mapped, the rest is LLM copy. WU-10/11 own the feature ACs; keeping these small makes later additive changes non-breaking. | Rich cards (dates, prices, images): invented specifics, and churn before the features are specified. **See Q2.** |
| D9 | **Envelopes** (§5): `ExtractRequest { message, currentProfile?, referenceDate }`; `ExtractResponse` = discriminated union on `status` (`needs_clarification` with `violations` (min 1) + `clarificationQuestion`; `ready`); `RecommendRequest { profile, referenceDate }`; `PresentRequest { profile, recommendations: Recommendation[] }`; `HealthResponse { status: 'ok', backend: 'nextjs'\|'fastapi'\|'go', contractVersion }`; `ErrorResponse { error: { code: ErrorCode, message } }` with `ErrorCode` = `VALIDATION_FAILED` (422), `LLM_REFUSAL`, `LLM_UPSTREAM_ERROR` (502), `INTERNAL_ERROR` (500). | §5 table and status codes; `LLM_REFUSAL` from §8.2. A closed `ErrorCode` enum lets clients map errors exhaustively; adding one is a `feat`. | Free-string error codes: clients can't switch on them safely. |
| D10 | **Constants** live in `src/wire/constants.ts` (`CONTRACT_VERSION`, `MIN_POPULATED_FIELDS = 3`) and are written to `generated/constants.json` as `{ contractVersion, minPopulatedFields }`. | §4.7. | — |
| D11 | **`buildFixture(schema, value)`** in `src/wire/build-fixture.ts`, exported from `./wire`: returns the parsed value typed as `z.output<S>`, or throws an `Error` listing every issue as `path: message`. One helper for domain-schema fixtures, backend test doubles, msw handlers and Playwright `page.route` payloads. | §6.1: mocks can't drift because they fail at construction. It is plain Zod, safe for `apps/` (see Q3). | A separate `./testing` export: a third entry in the "enforced" §4.2 map for a ten-line function. |
| D12 | **Generator code is tooling, outside `src/`**: `gen/artifacts.ts` (pure: `buildArtifacts(): Map<relativePath, string>`, deterministic, LF, trailing newline, 2-space JSON) and `gen/cli.ts` (`gen` writes files and deletes stale ones in `generated/`; `gen --check` compares in memory against disk and exits 1 listing missing, changed and stale files, with "run `pnpm --filter @vp/domain-schema gen`"). Root `gen:check` replaces the WU-02 stub with `pnpm --filter @vp/domain-schema gen:check`. | WU DoD: changing a schema without `gen` fails `verify`. Comparing in memory needs no git and also catches unstaged edits. Same placement rule as `scripts/` (WU-02 D2): tooling is proven by its tests, not measured by coverage; `src/` stays the contract. | `git diff --exit-code` after regenerating: rewrites the working tree inside `verify`, and misses untracked stale files. |
| D13 | **Run TypeScript tooling with plain `node`.** Node 24.22 strips types natively (checked: no flag, no warning). Relative imports in `domain-schema` use explicit `.ts` extensions; its `tsconfig.json` adds `allowImportingTsExtensions: true` and `erasableSyntaxOnly: true` (no enums/namespaces that stripping can't handle), and includes `gen` and `test`. | §3: Windows + POSIX, no extra runner. | `tsx`: another dependency for the same thing. Extensionless imports: Node's ESM loader rejects them. |
| D14 | **Construct rules are enforced by tests, two ways** (WU DoD "no refinements or transforms"). (a) **Zod walk** over every registered schema: fails on def types `transform`, `pipe`, `default`, `prefault`, `catch`, `date`, `bigint`, `lazy`, `custom`, `map`, `set`, `promise`, `function`, and any check of kind `custom` (that is what `.refine()`/`.superRefine()` add; they vanish silently from JSON Schema, so only a Zod walk sees them). (b) **JSON keyword walk** over the *generated* schema of each LLM-facing schema (D7): fails on `minimum`/`maximum` (other than ±`MAX_SAFE_INTEGER`), `exclusiveMinimum`/`exclusiveMaximum`, `multipleOf`, `minLength`, `maxLength`, `pattern`, `format`, `minItems`, `maxItems`, `uniqueItems`, `prefixItems`, `default`, `propertyNames`, object-valued `additionalProperties`, or any object property missing from `required`. | §4.1 and §4.4, checked on what is actually emitted, in a language-neutral way. Each walker is proven by a deliberately bad schema in the same test file. | A custom ESLint rule: catches `.refine(` text, not semantics, and nothing for the LLM-facing keyword list. |
| D15 | **Parity test with Ajv** (`ajv` **8.20.0**, `ajv/dist/2020`, `ajv-formats` **3.0.1**, strict mode on). A sample table `test/samples.ts` gives every registered schema ≥1 valid and ≥1 invalid sample; the test asserts the table covers every registry id, and that Zod `safeParse` and Ajv agree on every sample. `ajv` and `ajv-formats` go in the catalog because WU-07 uses the same validator. | WU required tests: "valid and invalid samples per schema" and "generated JSON Schema accepts and rejects the same samples as Zod". | A second validator per test: no gain. |
| D16 | **Dependencies** (all exact): catalog adds `zod 4.6.7`, `ai 7.0.154`, `@ai-sdk/anthropic 4.0.89`, `@ai-sdk/react 4.0.158`, `react`/`react-dom 19.3.1` (ADR 0001; unused until WU-08/12 but pinned once), `ajv 8.20.0`, `ajv-formats 3.0.1`, `yaml 2.9.1`. `domain-schema`: `dependencies.zod: catalog:`; devDeps `vitest`, `@types/node`, `ajv`, `ajv-formats`, `yaml` (all `catalog:`). | §3 exact pins, one zod (`pnpm why zod`). | — |

## 6. Risks & open questions

- **Q1 — `DATE_VALID` covers flexible `month` 1–12 (D6).** Recommended. It edits CLAUDE.md §4.6 wording. Alternative: a new `MONTH_RANGE` code.
- **Q2 — Provisional recommend/present shapes (D8).** They are deliberately minimal so WU-10/11 can add fields as non-breaking `feat`s. If you'd rather WU-04 only define the four endpoint envelopes with these two payloads left as TODO, the contract can't be generated end to end; I recommend the minimal shapes.
- **Q3 — `apps/` needs runtime wire imports, not only types.** §5 says the client runs a final `safeParse` on the stream, and §6.1 fixtures go through `buildFixture`. Both need the Zod schemas at runtime, while §4.2 says `apps/` imports wire "**types** only (prefer `import type`)". I propose no change now and a WU-12 note: §4.2 should read "may import `@vp/domain-schema/wire` (schemas, types and `buildFixture`); never `rules`". The ESLint `consistent-type-imports` rule already does the right thing either way.
- **R1 — Next.js and `.ts` import extensions (D13).** `transpilePackages` in WU-06/WU-12 must handle `./x.ts` imports in `domain-schema`. TS supports it with `allowImportingTsExtensions` under `noEmit`; Next's compiler is expected to, but it's unproven here. Fallback if it fails: switch the gen script to `tsx` and use extensionless imports (a WU-06 note either way).
- **R2 — `z.int()` bounds in LLM-facing schemas.** Tolerated by D14 (b) because the spike showed they're harmless; if WU-08 cassettes show otherwise, swap to `z.number()` plus a rule.
- **R3 — Zod internals in the construct walker.** `_zod.def` is semi-internal. Pinned zod means it can't move silently; the walker's self-tests break loudly on an upgrade.
