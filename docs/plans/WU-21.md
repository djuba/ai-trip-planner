## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): a walking skeleton. The API runs on Cloud Run from the WU-20 image, in replay mode, with no API key and no LLM cost. Every merge to `main` builds and deploys the image and runs the provider contract tests against the service URL. It isn't a demo and nothing links to it. It proves the image, Terraform, OIDC, CORS across real origins, streaming through the platform's front end, timeouts and cold starts long before launch (WU-23).

**In scope**
- **`infra/`** Terraform, with remote state in a GCS bucket. Bootstrapping the project, billing link and state bucket is a documented manual step. Resources:
  - the required project APIs;
  - an Artifact Registry Docker repository, with a cleanup policy that keeps the last few images;
  - the API service on Cloud Run: min 0, max 1 instance, a request timeout, a startup probe on `/v1/health`, `LLM_MODE=replay`, `WEB_ORIGIN`, public invocation;
  - a runtime service account with no roles;
  - Workload Identity Federation for this repository's deploy workflow on `main` only, and a deploy service account that can only push to that one repository and deploy that one service;
  - a billing budget with email alerts.
- **`.github/workflows/deploy.yml`**, on push to `main` (and `workflow_dispatch`): build and push the image, deploy it, run `pnpm test:contract:external` against the service URL. OIDC only; no stored secrets.
- **CI:** `terraform fmt -check` and `terraform validate` in a new `infra` job in `verify.yml`. Not in `pnpm verify`.
- **`infra/README.md`**: the runbook (bootstrap, `plan`/`apply`, rollback to an earlier image, teardown).
- **`infra` commit scope:** `commitlint.config.js`, its test, CLAUDE.md §10.
- **CLAUDE.md** §2 (`infra/`, `deploy.yml`), §3 (Terraform commands), §6.7 (the deploy workflow and the `infra` job).
- **README:** `infra/` in "Where to find things", a "How the design is checked" row for the post-deploy contract check, described as a deployment check with no URL.
- **ADR 0005:** a short addendum for the decisions this unit makes (D4, D5, D7), since the ADR owns hosting.

**Out of scope**
- Live mode, the API key in Secret Manager, the Anthropic spend limit (WU-23).
- The web service and its image (WU-12 Note / WU-23).
- The invite-code gate (WU-22). If WU-22 lands first, the post-deploy check needs a code (WU-22's open question); this unit doesn't solve that.
- A custom domain, Cloud Armor, performance testing (Backlog).
- Anything that reads as a demo link: no URL in the repo or in public CI logs (D6).

## 2. Approach & key decisions

**D1. Terraform owns the infrastructure; the deploy workflow owns only the image.** The `google_cloud_run_v2_service` sets everything (scaling, timeout, probe, env, service account), with `lifecycle { ignore_changes }` on the container image and the `client`/`client_version` fields that `gcloud` writes. The workflow runs `gcloud run services update --image=<digest>` and changes nothing else. So a deploy leaves `terraform plan` clean (DoD), and env or scaling changes go through Terraform, never through CI.
*Rejected:* Terraform deploys the image too (a `-var image=…` apply from CI). CI would need a Terraform-capable identity with IAM admin over the project, which is far more power than pushing an image needs (ADR 0005 §6). *Rejected:* Terraform applied from CI on merge, for the same reason; applies stay manual and local (the runbook).

**D2. First create uses a placeholder image.** The registry is empty on the first apply, and there's no Docker on the dev machine to push one. The service is created with Google's public sample `us-docker.pkg.dev/cloudrun/container/hello` (a variable, ignored after creation per D1). The first deploy-workflow run replaces it. The hello sample answers 200 on every path, so the `/v1/health` startup probe passes (R2 if not).

**D3. Service settings** (ADR 0005 §4; the WU-20 Note on the image):
- region `us-central1` (a Cloud Run free-tier region; Q3);
- `min_instance_count = 0`, `max_instance_count = 1`; request-based billing (`cpu_idle = true`); 1 vCPU, 512 MiB; default concurrency;
- container port 8080; startup probe `GET /v1/health` (period 2 s, failure threshold 30, so a cold start has up to a minute);
- `timeout = 300s`, a variable. WU-10 hasn't measured the worst-case `/recommend` latency yet (its Note), so 300 s (Cloud Run's default, well above two revise cycles of a Sonnet call in replay or live) is the starting value; WU-10/WU-23 revisit it. Proposed Note for WU-10 and WU-23;
- env: `LLM_MODE=replay`, `WEB_ORIGIN` (a variable, default `http://localhost:3000`: there's no web service yet, and a localhost origin grants no browser on the internet anything), and the **`MODEL_*` values from `CONTRACT_TEST_ENV`** (`test-model-fast`, …). Cassette keys hash the request body, which includes the model ID, so the contract suite's cassettes (from WU-09) only replay if the hosted service uses the same IDs the contract runner does (WU-20 D4). WU-23 switches them to the real IDs with `LLM_MODE=live`. Proposed Note for WU-23;
- `allUsers` gets `roles/run.invoker`, so the contract suite (and later the browser) can call it. It's public but unadvertised, replay-only, and capped at one instance;
- ingress all; the default `*.run.app` URL (ADR 0005 §9).

**D4. Least-privilege IAM** (the work breakdown asks for close review here):
- **Runtime SA** `api-runtime`: no project roles. Replay mode needs none; WU-23 adds `secretmanager.secretAccessor` on the one key secret.
- **Deploy SA** `github-deploy`, with resource-level bindings only:
  - `roles/artifactregistry.writer` on the one repository;
  - `roles/run.developer` on the one service (deploy revisions, read its URL and env; can't change IAM on it);
  - `roles/iam.serviceAccountUser` on the runtime SA only (needed to deploy a revision that runs as it).
  No project-level role, no `iam.serviceAccountTokenCreator` on anything else, no key.
- **APIs enabled by Terraform:** `run`, `artifactregistry`, `iam`, `iamcredentials`, `sts`, `cloudresourcemanager`, `serviceusage`, `billingbudgets`.
- **Workload Identity pool and OIDC provider** for `https://token.actions.githubusercontent.com`. The provider's `attribute_condition` admits only tokens where `assertion.repository_id == "1434919116"` (the numeric ID, so a rename or a new repo with the same name can't match), `assertion.ref == "refs/heads/main"`, and `assertion.workflow_ref` is this repo's `deploy.yml` on `main`. The deploy SA's `roles/iam.workloadIdentityUser` is granted to `principalSet://…/attribute.repository_id/1434919116` only. So only the deploy workflow, run from `main` of this repository, can become the deploy SA. `verify.yml`'s jobs request no `id-token` permission and get no cloud access (ADR 0005 §6).
*Rejected:* a deploy SA with project-level `run.admin`/`artifactregistry.admin`: it could change IAM and delete things. *Rejected:* a JSON key in a GitHub secret: the DoD forbids long-lived keys.

**D5. State, identifiers and what's committed.** The repository is public, so the project ID, project number and billing account ID stay out of it (they aren't secrets, but committing them advertises the environment and it isn't needed):
- `infra/backend.hcl` (bucket name) and `infra/terraform.tfvars` (project ID, billing account ID, alert email if any) are git-ignored; `*.example` versions are committed. `terraform init -backend-config=backend.hcl`.
- The deploy workflow reads three **GitHub Actions variables** (not secrets): `GCP_PROJECT_ID`, `GCP_WIF_PROVIDER` (the provider's resource name), `GCP_DEPLOY_SA`. Terraform outputs them; the runbook sets them with `gh variable set`. Region, repository and service names are fixed in the workflow.
- `.terraform.lock.hcl` is committed (provider pins, for `linux_amd64` and `windows_amd64`).
- The state bucket is versioned, uniform-access, public-access-prevented; created by the bootstrap step (it can't hold its own state).
*Rejected:* committing the IDs in `terraform.tfvars`: simpler, but it puts the environment's coordinates in a public repo for no gain.

**D6. The deploy workflow** (`deploy.yml`):
- triggers: `push` to `main`, `workflow_dispatch`; `concurrency: deploy` with `cancel-in-progress: false` (a deploy is never cut off half way); `permissions: contents: read, id-token: write`; `timeout-minutes: 25`.
- steps: checkout → `google-github-actions/auth` (WIF, no key) → `setup-gcloud` → `gcloud auth configure-docker us-central1-docker.pkg.dev` → `docker build --platform linux/amd64` tagged with the commit SHA, push → `gcloud run services update --image=<registry>/api-nextjs@<digest>` (deploy by digest, so what was pushed is what runs) → read the service URL and its `WEB_ORIGIN` with `gcloud run services describe` (one source of truth: Terraform's env) → **`echo "::add-mask::$URL"`**, because the repo's Actions logs are public and the contract runner prints its target → pnpm, Node, `pnpm install --frozen-lockfile` → `pnpm test:contract:external` with `API_BASE_URL` and `WEB_ORIGIN` set.
- every action is pinned to a commit SHA, as in `verify.yml`.
- No retries around the check: a cold start is covered by the startup probe (Cloud Run holds the first request until the instance is ready), so a failure means something is wrong.
*Rejected:* deploy with `--no-traffic --tag candidate`, check the tagged URL, then promote. It's the safer pattern for a live service, but pre-launch nothing depends on the service, and it adds traffic-tag drift to manage in Terraform. Proposed as a WU-23 Note, when the service goes live.
*Rejected:* reusing `pnpm test:image`'s build: the deploy needs the image pushed to the registry, and the `image` job has no cloud access by design.

**D7. Budget alert.** `google_billing_budget` on the billing account, scoped to this project, amount $5 (a variable), thresholds 20 %, 50 %, 100 % of actual spend and 100 % forecast. Alerts go to the billing account's admins by email (the default), so no address is stored. GCP has no hard cap; this is the early warning (ADR 0005 §7). Creating it needs the applying user to hold Billing Account Administrator (or Costs Manager) on the billing account, and the Budget API needs a quota project with user credentials (`user_project_override`, `billing_project`; R4).

**D8. CI checks for Terraform: a third job, `infra`, in `verify.yml`.** `hashicorp/setup-terraform` (pinned, Terraform version pinned to match `required_version`), then `terraform fmt -check -recursive` and `terraform init -backend=false` + `terraform validate` in `infra/`. No credentials. Q4 asks whether it becomes a required check (recommended: yes). `pnpm verify` stays Terraform-free.

**D9. ACs live in this plan**, as in WU-20: no user-facing feature, so no `docs/features/` file. Most ACs are proven by the hosted run itself, not by gated tests. The one piece of code that would be worth unit-testing (the WIF condition) is Terraform, proven by the deploy succeeding from `main` and by AC-HOST-05's negative check.

**D10. How the deploy path is proven before merge** (Q2). The workflow only runs on `main`, and the WIF condition only admits `main`, so the DoD's "a merge deploys" can only fully happen after merge. Recommended, on the WU-20 pattern: iterate on a scratch branch `scratch/wu-21-deploy` whose copy of `deploy.yml` also triggers on that branch, with the WIF condition temporarily widened to that ref (a local apply). Once the scratch run is green (deploy + contract check), narrow the condition back to `main` (apply again), delete the scratch branch, and confirm `terraform plan` is clean. The WU branch's workflow is the scratch one minus that trigger. After you merge, I watch the first `main` run and report it.

2. **A unit test for the service's configuration (new file).** `scripts/infra-config.test.ts` checks that `infra/service.tf` sets `LLM_MODE` and the `MODEL_*` IDs equal to `CONTRACT_TEST_ENV`, that `WEB_ORIGIN` comes from the variable the workflow reads back, and that the workflow path in the identity condition exists. Deviation 1 showed the IDs can drift; a text check needs no Terraform in `pnpm verify`. It lands with the Terraform (commit 3).
3. **The deploy's output is kept, not discarded (plan-review #1).** The URL is read and masked before the deploy step, so `gcloud run services update`'s "Service URL" line is already masked. Keeping its output keeps deploy errors readable.
4. **Masking can't cover the masking step itself (plan-review #2), raised with you.** GitHub prints a step's `env:` values in its log header, so the step that registers the masks prints the three variables once, unmasked. The provider name holds the project number, and new-style Cloud Run URLs are `https://<service>-<project number>.<region>.run.app`, so the URL could be derived from that one line. Only Actions secrets are masked from the start.
   **Decided (2026-11-13): option (b).** The three identifiers are repository *secrets*, not variables, so GitHub masks them everywhere; the first step masks only the project number derived from them. None is a credential. AC-HOST-04 reads "no secret holds a credential" (the three are identifiers), and CLAUDE.md §6.7's "CI never holds secrets" becomes "CI holds no credentials". `infra/README.md`, `outputs.tf` and the ADR addendum say so.
5. **The Budget API is enabled during bootstrap (runbook).** Terraform calls it with the project as quota project before its own `google_project_service` could enable it, so `billingbudgets.googleapis.com` joins the bootstrap's `gcloud services enable`.
6. **Deploy proof on the scratch branch (D10), as planned.** Run 1 (condition not yet widened) failed at `auth` with "The given credential is rejected by the attribute condition" (AC-HOST-05). After widening, run 2 passed first time: build, push, deploy by digest, and 24 contract tests passed (1 skipped) against the hosted URL (AC-HOST-01, -02). Narrowing back changed only the provider's condition, and `plan` was then clean (AC-HOST-03). Both service accounts have 0 user-managed keys, and the only repository secrets are the three identifiers (AC-HOST-04). The scratch branch is deleted.
