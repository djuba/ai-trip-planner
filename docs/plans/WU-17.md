## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): limit what prompt injection and API abuse can achieve. Every free-text value the API accepts or returns has a cap. Oversized input is rejected at the wire, and an injected instruction that gets past the model can yield only a few short strings, never free-form output paid for with our tokens.

**In scope**
- The length spike (TS only, per the WU-19 Note): how Zod `.max()` and Ajv `maxLength` count. Already run during planning (§2 D1); CP2 locks the result in with parity samples.
- ADR 0004, with a **Future hardening** section.
- Cap constants in `packages/domain-schema/src/wire/constants.ts`, copied into `spec/generated/constants.json`.
- `.max()` on every string and array reachable from `TripProfile`, and on `ExtractRequest.message`. `TripProfile` is shared, so `ExtractRequest.currentProfile`, `RecommendRequest.profile`, `PresentRequest.profile` and `ExtractResponse.profile` all get the caps at once. Regenerate `spec/generated/`.
- `contractVersion` 0.3.0 → 0.4.0 (stricter request schemas are breaking; §2 D7).
- CLAUDE.md §4.4, §4.5, §4.7 wording.
- `normalize` discards over-cap strings and list items, and reports what it discarded.
- Conformance checks: 200 at exactly the cap, 422 at the cap plus one, for `message` and two profile fields, plus a self-test case.
- `docs/features/input-limits.md` with AC IDs.

**Out of scope**
- Caps on `ExtractionSchema` (ADR 0001 Q3: constraints in a model schema turn one bad value into a 502).
- `RecommendationSet` / `PresentationModel` / `clarificationQuestion` strings (WU-10, WU-11, WU-09 per their Notes).
- Logging what `normalize` discarded, and sizing `maxOutputTokens` from the caps (WU-09 Notes).
- The web input's `maxlength` (WU-13).
- Everything in the Future hardening list (backlog, WU-09, WU-18).

## 2. Approach & key decisions

**D1. Length = Unicode code points. Zod and Ajv already agree.** Spike, run while planning against the pinned versions (zod 4.6.7, ajv 8.20.0):

| Input | Zod `.max(3)` | Ajv `maxLength: 3` |
|---|---|---|
| `'🌴🌴🌴'` (3 code points, 6 UTF-16 units) | accept | accept |
| `'éé'` (4 code points, 2 graphemes) | reject | reject |

Zod 4 counts with `util.codePointLength` once the UTF-16 length passes the limit; Ajv uses `ucs2length` (its `unicode: false` option, which counts units, is deprecated). Both count a lone surrogate as one. JSON Schema defines `maxLength` in characters per RFC 8259, i.e. code points, which is also what Python `len()` and Go `utf8.RuneCountInString` give, so a future backend generated from `spec/` agrees too. Graphemes are rejected: no JSON Schema validator counts them. ADR 0004 records the table; CP2 adds parity samples at the cap in astral characters and combining marks so a library upgrade that changes counting fails `parity.test.ts`. The outdated comment on `longMessage` in `samples.ts` ("a length cap would disagree across languages") is corrected. (CLAUDE.md §4.1.)

**D2. Cap values: well above honest use, small enough that injected output stays short.** Proposed (Q1):

| Constant | `constants.json` key | Value | Applies to |
|---|---|---|---|
| `MAX_MESSAGE_LENGTH` | `maxMessageLength` | 2000 | `ExtractRequest.message` |
| `MAX_SHORT_TEXT_LENGTH` | `maxShortTextLength` | 100 | `region`, `departure.city`, `people[].gender`, each `unmappedExperiences` item |
| `MAX_NOTE_LENGTH` | `maxNoteLength` | 300 | `dateRange.note` (flexible) |
| `MAX_DATE_TEXT_LENGTH` | `maxDateTextLength` | 32 | fixed `dateRange.start` / `end` |
| `MAX_EXPERIENCES` | `maxExperiences` | 20 | `experiences` item count (10 enum values; duplicates are not a contract error) |
| `MAX_UNMAPPED_EXPERIENCES` | `maxUnmappedExperiences` | 10 | `unmappedExperiences` item count |
| `MAX_PEOPLE` | `maxPeople` | 50 | `people` item count |

The date cap is 32, not 10: `DATE_VALID` is a rule, so `"June 1st, 2027"` must still reach the rules and come back as `needs_clarification` (§4.5). Worst-case model-written free text in one profile is about 100·3 + 300 + 64 + 10·100 + 50·100 ≈ 6.7k code points; `gender` dominates, so Q1 offers a smaller gender cap. Flat keys in `constants.json` follow the existing `maxRequestBodyBytes`.

**D3. Caps go on the wire; business rules stay off it.** A cap is a resource limit, not a business rule: a 2 MB region is abuse, not a clarification. So caps are `.max()` in the wire schema (JSON-Schema-expressible, §4.1) and failures are 422 `VALIDATION_FAILED`, while range/format checks stay rules (§4.5). CLAUDE.md §4.5's "carry no range or format constraints on the wire" gets one exception sentence pointing to ADR 0004. Rejected: a `FIELD_TOO_LONG` rule returning `needs_clarification`. It would echo the oversized value back in the response and in the clarification prompt, which is the output we want to stop.

**D4. `ExtractionSchema` stays uncapped; `normalize` discards.** The model's schema gets no constraints (ADR 0001 Q3, CLAUDE.md §4.4). `normalize` drops anything over a cap, so a response always parses against `TripProfile` and the client can send it back next turn. Discard, never truncate: a truncated injected string is still injected text, and a cut-off city name is a wrong value presented as right. Discard granularity, smallest unit that keeps the shape valid:
- over-long `region`, `departure.city`, `people[i].gender`, flexible `note` → that field is dropped (then the existing empty-object rules apply: a `departure` or flexible range with nothing left is dropped);
- over-long fixed `start` or `end` → the whole `dateRange` (both are required in the fixed variant);
- over-long `unmappedExperiences` item → that item, then the list if it is empty;
- a list over its count cap (after item drops) → the whole list (Q3). Keeping the first N is truncation, and an over-count list signals abuse rather than an honest request.

**D5. `normalize` returns `{ profile, discarded }`.** `discarded: Discarded[]`, each `{ path, reason, limit, actual }`: `path` a JSON Pointer in extraction coordinates (e.g. `/people/2/gender`), `reason` `'too_long' | 'too_many_items'`, `limit` the cap, `actual` the measured length or count. The value itself is not included, so logging it (WU-09) can't leak or amplify the payload. Order is deterministic (schema field order, then index). The type lives in `src/rules/` (backend-only, not wire). Rejected: a second `normalizeWithReport` function, which leaves a variant that silently drops the report. The only callers today are tests.

**D6. Discard tests are plain TS unit tests, not `spec/fixtures/normalize/`** (Q2). Discarding is server-internal: the contract only promises that responses parse against `TripProfile`, which the conformance suite and the parse-always test cover. With one backend (ADR 0003) shared fixtures buy nothing. ADR 0004 says so, and ADR 0003's "If a second backend is added" list gets one line, "normalize fixtures in `spec/fixtures/normalize/` (ADR 0004)", so the list stays the one place to look.

**D7. `contractVersion` 0.3.0 → 0.4.0**, committed as `feat(domain-schema)!:` with a `BREAKING CHANGE:` footer (CLAUDE.md §4.3, §10). Requests that were valid (a 3k-character message) now get 422. Pre-1.0, a breaking change bumps the minor, as in ADR 0003.

**D8. "Normalize output always parses" is a table-driven test, not property-based.** It builds an extraction with every capped field at the cap, at cap + 1, and in astral characters, plus one with everything over cap at once, and asserts `TripProfile.safeParse(normalize(x).profile).success` for each. Rejected: adding `fast-check` for one test.

**D9. Conformance boundary checks drive the backend over HTTP and use astral characters.** At exactly the cap in emoji (2 UTF-16 units each), the backend must answer 200, which proves it counts code points; at cap + 1, 422 `VALIDATION_FAILED`. Fields: `message` on `/extract`; `region` (string) and `people` (count) on the profile of every POST endpoint. Caps come from `constants.json`, bodies are validated by `assertSchema` like the existing request builders, and the 200 response is schema-checked. The fake backend already validates requests with Ajv against `spec/generated/`, so it picks up the caps; the self-test adds a fake that ignores caps and must fail the new check. The stubbed routes parse the request before answering, so 200-at-cap works today. (CLAUDE.md §6.5.)

**D10. Existing tests that build large valid bodies pad elsewhere.** `backends/api-nextjs/tests/integration/http-adapter.test.ts` pads `message` to ~1 MiB to test the 413 boundary. With a 2000-character cap that body would be 422. It moves the padding to an unknown top-level key (requests are open objects, AC in `samples.ts`), so the test still proves the byte boundary. Same commit as the cap (CP2), so the tree stays green.

## 6. Risks & open questions

- **R1. Stricter requests break nothing today.** No web client exists yet and `contracts/pacts/` is empty, so 0.4.0 has no consumer to break. WU-12's pact starts at 0.4.0.
- **R2. A cap that is too tight hurts honest users** only as a 422, which the web client (WU-13) prevents with `maxlength` from the same constant. Values are easy to raise later (raising a cap is non-breaking).
- **R3. Silent discard loses user data** in rare honest cases (a 101-character region). Acceptable at these values; WU-09 logs discards, and `INSUFFICIENT_DETAIL` asks again if too little is left.
- **Q1. Cap values** (D2 table). Option: `gender` at 30 instead of 100, cutting the worst case from ≈6.7k to ≈3.2k code points (needs an eighth constant, `MAX_GENDER_LENGTH`). Recommendation: accept the table as is; a smaller gender cap is cheap if you want it.
- **Q2. Normalize discard tests:** plain TS unit tests plus the ADR 0003 line (recommended, D6), or `spec/fixtures/normalize/`.
- **Q3. A list over its count cap:** drop the whole list (recommended, D4) or keep the first N.
- **Q4. `contractVersion` 0.4.0** (recommended, D7).
