# WU-05 — Invariant rules & fixtures: plan

**Status:** approved (2026-11-04) with the revisions in §9 · **Depends on:** WU-04 (done) · **Author:** main agent (Opus), 2026-11-04

## 1. Goal & scope

**Goal** (from `docs/work-breakdown.md`): every business invariant is specified language-neutrally and implemented in TS.

**In scope**
- `docs/features/trip-validation.md`: Given/When/Then ACs for each rule code, the populated-field definition and `normalize`.
- `packages/domain-schema/rules.md`: the language-neutral catalog from CLAUDE.md §4.6–4.7.
- `packages/domain-schema/src/rules/`: `evaluateRules`, `countPopulatedFields`, `normalize`.
- `packages/domain-schema/fixtures/`: input → expected `RuleViolation[]` cases, reused by the contract suite in WU-07.
- The two optional checks from the WU-05 Notes: `rules.md` codes match `RuleCode`, and every code has fixture cases.
- The §6.3 requirement that the generated JSON Schema round-trips the fixtures.

**Out of scope**
- Any wire schema change. `RuleViolation` params were fixed in WU-04, so there is no `gen` output change and no `CONTRACT_VERSION` bump. If implementation shows a schema change is needed, that is a material deviation and I stop and ask.
- Calling the rules from an endpoint or routing to `needs_clarification` (WU-09).
- Clarification text (WU-09).
- Driving the fixtures over HTTP (WU-07; see R1).
- Language-neutral `normalize` fixtures. `normalize` gets TS unit tests only; WU-05's scope lists only `RuleViolation[]` fixtures.

## 2. Approach & key decisions

| # | Decision | Why / CLAUDE.md | Rejected alternative |
|---|---|---|---|
| D1 | **`evaluateRules(profile: TripProfile, referenceDate: string): RuleViolation[]`**. It is pure and total: no clock, no throw, no input mutation. `referenceDate` is a precondition, already guaranteed by the wire (`z.iso.date()`). | §4.5, §4.6, §6.1. §4.5 writes `evaluateRules(profile)` as shorthand, so T5 updates that line. | A `{ referenceDate }` context object: no second field is planned. |
| D2 | **One check function per code, run from one ordered array in `evaluate.ts`.** Grouped in small modules: `people.ts`, `dates.ts`, `departure.ts`, `populated.ts`, plus `calendar.ts` for date arithmetic. | §9 no god modules. Each check is a `(profile, referenceDate) => RuleViolation[]`. | One big `rules.ts`; one file per code (eight near-empty files). |
| D3 | **Violation order is part of the rule spec:** catalog order of codes (§4.6 table), then document order within a code. Fixtures compare exact arrays. | Order feeds the clarification prompt (WU-09), so unstable order means unstable cassette keys (§8.3). A stated order is also trivial to port. | Set comparison: more lenient for other backends, but leaves prompt input undefined. |
| D4 | **Dependent rules are skipped, not stacked.** `DATE_ORDER` runs only when both fixed dates pass `DATE_VALID`. `DATE_NOT_PAST` compares only values that pass `DATE_VALID`: a past `start` still fires when `end` is malformed, and a flexible `year` still fires when `month` is invalid. | A comparison against a non-date is meaningless, and one bad value should produce one clear clarification. | Lexically comparing malformed strings: yields spurious violations. |
| D5 | **A flexible month with no year is never past (Q1).** It means the next occurrence of that month. Flexible month + year compares `YYYY-MM` with the reference's month, so the current month passes. Flexible year only compares `YYYY`, so the current year passes. | WU-05 Note: decide and write into `rules.md`. "March" said in November means next March; asking the user about it would be a pointless clarification. | Comparing against the reference year's months (the tentative WU-04 A6 wording): "March" in November would fire `DATE_NOT_PAST` with a made-up `YYYY-MM`. **Changes A6's tentative wording, so it is your call.** |
| D6 | **Violation paths:** `/people/<i>/age`; `/dateRange/start`, `/dateRange/end`, `/dateRange/month`, `/dateRange/year`, `/dateRange/durationNights` for `DATE_VALID`; `/dateRange/start` for a fixed `DATE_NOT_PAST`; `/dateRange` for a flexible `DATE_NOT_PAST` and for `DATE_ORDER` (they concern several fields); `/people` for `PARTY_HAS_ADULT`; `""` for `INSUFFICIENT_DETAIL`; `/departure/maxStops`. `rules.md` lists them and fixtures assert them. | §4.5 JSON Pointer; WU-05 Note: `path` points at the offending field. | — |
| D7 | **Date validity is specified as an algorithm, not a library call.** Exactly `DDDD-DD-DD` in ASCII digits with nothing after it, month 01–12, day within the month by the Gregorian leap rule. Implemented with arithmetic in `calendar.ts`; valid dates compare as strings. | Portability: `Date` silently rolls Feb 30 over, Python's `fromisoformat` rejects year 0000, and `$` matches before a trailing newline in Python. Fixtures include `2027-06-01\n`, `2027-6-1`, `2027-06-01T00:00:00Z`, `""` and `2100-02-29`. | `new Date()`: rolls over, reads local timezone. |
| D8 | **"Trimmed" means Unicode `White_Space`** in `rules.md`, implemented as `/\P{White_Space}/u.test(s)`. Fixtures pin U+00A0 and U+0085 (whitespace) and U+FEFF (not whitespace). | §4.7 says "trimmed", but `trim()`, Python `strip()` and Go `TrimSpace` disagree on U+0085 and U+FEFF. This is the kind of drift the project exists to catch, and it costs one regex. | Plain `trim()`: quietly makes JS the spec. |
| D9 | **`countPopulatedFields` follows §4.7 literally and ignores validity.** A fixed range counts even with malformed dates; climate counts when non-null. Maximum is 6. Flexible with only `durationNights` or `note` does not count. | §4.7 definition. The malformed date already raises `DATE_VALID`, so it isn't hidden. | Counting only valid fields: double-reports one problem. |
| D10 | **`normalize(extraction)` drops nulls and empty arrays, recursively, and nothing else.** `0` is kept (`maxStops`, `age`). It does not trim or drop empty strings: `evaluateRules` judges them. An all-null `departure` and an all-null flexible `dateRange` are dropped entirely. A flexible range with only `note` stays. Keys come out in schema order, so serialized profiles are stable for cassette keys. | §4.4, WU-05 Note on `departure`, §8.3. | Keeping `{ kind: 'flexible' }`: carries no information. Trimming: silently edits model output. |
| D11 | **Fixtures are plain JSON, one file per code:** `fixtures/rules/<CODE>.json`, an array of `{ id, ac, description, referenceDate, profile, expectedViolations }`. Each case is self-contained, with no shared base or inheritance. `status` is not stored: empty `expectedViolations` means `ready`, otherwise `needs_clarification` (`rules.md` states this). | §2, §4.6, §6.5: Python and Go read them without any TS. | YAML or TS builders: not language-neutral. |
| D12 | **The fixture loader lives in `test/rule-fixtures.ts`** and parses every file through `buildFixture` with a test-only `RuleFixtureFile` Zod schema (not in the registry, so it is not contract surface). | §6.1. WU-07 reads the JSON directly and validates with Ajv. | Adding it to `contractRegistry`: fixtures aren't an HTTP payload. |
| D13 | **Fixture tests are table-driven:** each case becomes `it(`${ac}: ${description}`)`. A traceability test reads `trip-validation.md` and asserts each AC ID appears in a fixture's `ac` or in an `it('AC-…` title in `src/rules/*.test.ts`. `grep AC-RULES-07 packages/domain-schema` finds both. | §6.2, WU-05 DoD. Reading titles from a Vitest reporter output would need a second test run. | Writing every fixture case again as a TS test. |
| D14 | **`rules.md` uses one `### <CODE>` heading per code,** each giving definition, path, params and fixture file. A test checks the headings equal `RuleCode.options`, each code has a fixture file, and each file has at least one case where the code fires and one where it doesn't. | WU-05 Note (optional check); §6.3 "at least one passing and one failing fixture". | Leaving prose and code unlinked. |
| D15 | **Fixtures round-trip the committed `generated/` schemas.** Each `profile` validates against `generated/TripProfile.schema.json` and each expected violation against `generated/RuleViolation.schema.json`, using Ajv set up as in `parity.test.ts`. `evaluateRules`' actual output is also `safeParse`d against `RuleViolation`. | §6.3 explicitly asks for this. It also proves §4.5: bad values such as a child aged 18 or month 13 stay valid on the wire. | — |
| D16 | **Rule bounds are private constants in `src/rules/`** (child 0–17, adult 18–120, year 2000–2100), restated in `rules.md`. Only `MIN_POPULATED_FIELDS` stays shared, via `generated/constants.json`. | §4.7 names just that constant. Exporting more means a contract change for no consumer. | Moving them to `constants.ts`: changes `generated/`. |

## 6. Risks & open questions

- **Q1 — A flexible month with no year is never past (D5).** Recommended. It replaces the tentative wording in WU-04 A6 and adds a line to CLAUDE.md §4.6. WU-09/WU-10 then read a month-only date as its next occurrence. Alternative: compare against the reference year, which makes "March" in November need a clarification.
- **R1 — How does WU-07 run these fixtures over HTTP?** §6.5 says conformance sends every fixture to `API_BASE_URL`, but no endpoint evaluates a given profile deterministically. `/extract` puts the LLM between the input and the rules, so cassettes are backend-specific because they hash the prompt. `/recommend`'s behavior on a profile that isn't `ready` is undefined. This unit keeps the fixture format transport-neutral and doesn't solve it. I propose a Note on WU-07 to decide the mechanism, and a Note on WU-10 to define `/recommend` on a non-`ready` profile. Raising it now in case you'd rather settle it here.
- **R2 — A fixed date has no year bound.** `DATE_VALID` bounds only the flexible `year` (§4.6), so `9999-01-01` is valid and `0000-01-01` is valid and past. Kept as written. Tightening it would be a separate rule change.
- **R3 — T3 and T2 may disagree.** That is the point of the split, but it can cost a round of arbitration in T5.
- **R4 — Traceability checks text, not passing tests.** `catalog.test.ts` proves each AC ID exists in a test title or fixture, and `pnpm verify` proves those tests pass. Combined, they meet the DoD; a skipped test would slip past, so T5 greps for `.skip` and `.only`.
