# Conversation UI: acceptance criteria

How a user talks to the planner in `apps/web-nextjs` until their trip profile is `ready`. The design is in [the WU-13 plan](../plans/WU-13.md) (D1–D13 and the fixes at approval). The client holds the whole conversation: the server is stateless (CLAUDE.md §5), so every turn sends the current profile, and every response's profile replaces it. Calls go through the typed client ([`web-client.md`](web-client.md)). Violations and enum values are worded from the spec's message catalog ([`message-catalog.md`](message-catalog.md)). Recommendations and cards are in [`presentation-ui.md`](presentation-ui.md).

## Acceptance criteria

- **AC-CONV-01:** Given an empty conversation, when the user sends a message, then `POST /v1/trip/extract` gets `{ message, referenceDate }`: the message as typed, the browser's local date as `YYYY-MM-DD`, and no `currentProfile`. The user's message appears in the thread, and the composer is cleared.
- **AC-CONV-02:** Given a `needs_clarification` response, then the thread shows `clarificationQuestion` as plain text (markup in it shows literally, never as HTML), and under it a "What needs fixing" list with one item per violation, worded from the message catalog with the violation's `params` and `field`.
- **AC-CONV-03:** Given a profile from an earlier response, when the user sends the next message, then the request's `currentProfile` is that profile exactly. When the response arrives, its `profile` replaces the client's copy: a field the response leaves out disappears from the profile panel.
- **AC-CONV-04:** Given a `ready` response, then the thread shows that the trip profile is ready, the profile panel shows the whole profile, and the composer stays open for corrections.
- **AC-CONV-05:** Given any violation of any of the 8 rule codes, then its text is the catalog's template formatted with its params and `field`. Given an enum value (experience, climate, travel mode, traveler type), then it shows its catalog label.
- **AC-CONV-06:** Given no profile yet, then the panel says there is nothing yet. Given a profile, then the panel shows each populated field (from, when, where, climate, experiences, also asked for, travelers) and none of the absent ones. Given violations, then each field that a violation's `path` points into is marked as needing attention; a violation at `""` marks none.
- **AC-CONV-07:** Given the composer, then it shows how many characters are left of `MAX_MESSAGE_LENGTH`, counted in code points (an emoji counts as one). A message of exactly `MAX_MESSAGE_LENGTH` emoji can be sent; one more cannot, and the composer says why. A blank message cannot be sent. The field has no `maxlength` attribute.
- **AC-CONV-08:** Given a turn in flight, then the conversation shows a "Planning…" status and Send is disabled. When the user chooses Start over, then the request is aborted, and the thread, the profile and any error are cleared.
- **AC-CONV-09:** Given an `upstream`, `network`, `server`, `contract` or `invalid_request` error, then an alert explains it and offers Retry. Retry sends the identical request again, including the same `currentProfile`, without adding a second copy of the user's message. The profile is kept, and the composer is usable again.
- **AC-CONV-10:** Given no stored invite code, then no code entry is shown before a 401. Given a 401 with no stored code, then a labelled code entry appears; submitting a code stores it and retries the turn with `authorization: Bearer <code>`. Given a 401 when a code is stored, then the entry says that code isn't valid.
- **AC-CONV-11:** Given the page is opened with `?invite=<code>`, then the code is stored and removed from the address bar (other query parameters and the hash stay), no code entry is shown, and the first request carries it. If that code gets a 401, then the entry says it isn't valid.
- **AC-CONV-12:** Given a 429 `RATE_LIMITED` with `Retry-After`, then the alert says to try again in about that long (minutes, or seconds under a minute), or "in a little while" without one, and offers Retry. Given a 429 `QUOTA_EXHAUSTED`, then it says the invite has been used up, with no Retry. Given a 413, then it says the message is too long, with no Retry.
- **AC-CONV-13:** Given a stored code, then it survives a reload in the same tab (session storage). Given storage that throws, then the code is kept in memory for the page's life.
- **AC-CONV-14:** Given each state (empty, sending, clarification, ready, error, code entry, code rejected, quota used up), then the page has no axe violations.
